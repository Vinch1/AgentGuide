## 第一部分：Agent 基础概念

**Q1: 你如何定义一个基于 LLM 的智能体（Agent）？它通常由哪些核心组件构成？**
- 难度：⭐⭐
- 岗位：通用
- 标签：#Agent #定义 #架构
- 公司：所有公司（必考）

**参考答案：**

基于 LLM 的智能体（Agent）是一个能够**自主感知环境、做出决策并采取行动**以完成目标任务的系统。与传统 LLM 只做"单轮问答"不同，Agent 具备自主规划和执行能力。

核心组件通常包括以下四个：

1. **规划（Planning）**：将复杂任务拆解为可执行的子步骤。常用技术包括 Chain-of-Thought（CoT）、Tree-of-Thought（ToT）、ReAct 等。规划模块决定了 Agent "想做什么"。
2. **记忆（Memory）**：
   - **短期记忆**：当前对话上下文、中间推理结果，通常用上下文窗口直接承载。
   - **长期记忆**：跨会话的知识与经验，通常借助向量数据库（如 Milvus、Pinecone）、知识图谱或关系数据库进行持久化存储。
3. **工具调用（Tool Use）**：Agent 通过 Function Calling 调用外部 API、搜索引擎、代码执行器等工具，扩展其能力边界。这是 Agent 区别于纯语言模型的关键——它能"动手做事"。
4. **感知与行动（Perception & Action）**：接收外部输入（文本、图像、API 返回等），并将决策转化为具体操作（发消息、调接口、执行代码等）。

一个典型的 Agent 执行循环为：**感知 → 规划 → 行动 → 观察 → 反思 → 继续规划**，形成闭环。

> 面试加分点：可以结合具体项目说明你用的 Agent 架构，以及各模块在工程中的实际实现方式。

**Q2: 请详细解释 ReAct 框架。它是如何将思维链和行动结合起来，以完成复杂任务的？**
- 难度：⭐⭐⭐
- 岗位：通用
- 标签：#Agent #ReAct #核心范式
- 公司：字节、阿里、腾讯（高频）

**参考答案：**

ReAct（Reasoning + Acting）是 Yao et al. (2022) 提出的一种将**推理（Reasoning）**和**行动（Acting）**交替进行的 Agent 范式，核心思想是让 LLM 在回答复杂问题时，边思考边调用工具。

**工作流程：**

```
问题: "2024年奥斯卡最佳影片的导演是谁？他之前的代表作是什么？"

Thought 1: 我需要先查到2024年奥斯卡最佳影片是哪部。
Action 1: Search["2024年奥斯卡最佳影片"]
Observation 1: 《奥本海默》获得2024年奥斯卡最佳影片。

Thought 2: 现在我知道是《奥本海默》，需要查导演信息。
Action 2: Search["奥本海默 导演"]
Observation 2: 导演是克里斯托弗·诺兰。

Thought 3: 我需要查诺兰的代表作。
Action 3: Search["克里斯托弗·诺兰 代表作"]
Observation 3: 代表作包括《盗梦空间》《星际穿越》《蝙蝠侠：黑暗骑士》等。

Thought 4: 我已经获得了所有需要的信息，可以给出最终答案。
Answer: 2024年奥斯卡最佳影片《奥本海默》的导演是克里斯托弗·诺兰，他的代表作包括《盗梦空间》《星际穿越》《蝙蝠侠：黑暗骑士》等。
```

**ReAct 与纯 CoT 的关键区别：**
- CoT（Chain-of-Thought）只在"脑内"推理，不与外界交互，容易产生幻觉。
- ReAct 将推理步骤与工具调用交织在一起，通过 Observation 获取真实信息，**大幅降低幻觉率**。

**实现要点：**
1. Prompt 设计：在 system prompt 中明确告诉 LLM 输出 `Thought → Action → Observation` 的格式。
2. Action 解析：用正则或结构化解析从 LLM 输出中提取动作和参数。
3. 工具执行：根据解析结果调用对应工具，将结果拼回 prompt 作为 Observation。
4. 循环终止：设置最大迭代次数（通常 5-10 轮），防止死循环。

> 面试加分点：说明 ReAct 的局限性（如多轮调用延迟高、工具调用失败时的容错），以及你在实际项目中是如何优化的。

**Q3: 在 Agent 的设计中，"规划能力"至关重要。请谈谈目前有哪些主流方法可以赋予 LLM 规划能力？（例如 CoT, ToT, GoT等）**
- 难度：⭐⭐⭐
- 岗位：通用
- 标签：#Agent #规划 #思维链
- 公司：字节、阿里（高频）

**参考答案：**

赋予 LLM 规划能力的主流方法如下：

**1. Chain-of-Thought（CoT）—— 线性推理链**
- Wei et al. (2022) 提出，通过在 prompt 中加入"Let's think step by step"或给出推理示例，引导 LLM 将复杂问题分解为连续的中间步骤。
- **优点**：简单高效，zero-shot CoT 几乎零成本。
- **缺点**：只能探索单条推理路径，如果某一步走错，无法回溯。

**2. Tree-of-Thought（ToT）—— 树状搜索**
- Yao et al. (2023) 提出，将推理过程建模为搜索树，每个节点是一个推理状态，可从多个方向展开。
- 支持 BFS（广度优先）或 DFS（深度优先）搜索，配合 LLM 自我评估来剪枝。
- **优点**：能回溯错误路径，适合需要探索多方案的规划任务（如24点游戏、创意写作）。
- **缺点**：LLM 调用次数成倍增加，延迟和成本显著上升。

**3. Graph-of-Thought（GoT）—— 图状推理**
- Besta et al. (2023) 提出，在 ToT 基础上允许不同推理分支之间合并、聚合。
- **优点**：最灵活，适合需要综合多条推理线索的复杂任务。
- **缺点**：实现复杂度最高。

**4. Plan-and-Solve —— 两阶段规划**
- 将规划分为两步：先生成整体计划（Plan），再逐步执行（Solve）。
- 实践中常用"先让 LLM 输出任务列表，再逐一执行"的方式实现。

**5. Reflexion —— 反思式规划**
- Shinn et al. (2023) 提出，Agent 执行任务后进行自我反思，将失败经验存入记忆，指导下一次尝试。
- 本质上是将"试错+反思"引入规划过程。

**对比总结：**

| 方法 | 搜索结构 | 回溯能力 | 调用成本 | 适用场景 |
|------|---------|---------|---------|---------|
| CoT | 线性链 | ❌ 无 | 低 | 通用推理 |
| ToT | 树状 | ✅ 有 | 中-高 | 多方案探索 |
| GoT | 图状 | ✅ 有 | 高 | 复杂综合推理 |
| Plan-and-Solve | 两阶段 | 部分 | 低 | 任务分解 |
| Reflexion | 迭代式 | ✅ 有 | 中 | 自适应优化 |

> 面试加分点：结合项目说明你实际用了哪种方法，以及为什么选它（比如选 CoT 是因为延迟敏感，选 ToT 是因为需要高质量输出）。

## 第二部分：Memory 系统设计

**Q4: Memory 是 Agent 的一个关键模块。请问如何为 Agent 设计短期记忆和长期记忆系统？可以借助哪些外部工具或技术？**
- 难度：⭐⭐⭐
- 岗位：通用
- 标签：#Agent #Memory #系统设计
- 公司：字节、阿里、腾讯（高频）

**参考答案：**

Agent 的记忆系统设计分为短期记忆和长期记忆两个层次：

**1. 短期记忆（Short-term Memory）**
- **本质**：就是当前 LLM 的上下文窗口（Context Window）。
- **内容**：当前对话的历史消息、系统提示词、中间推理结果、最近的工具返回。
- **管理策略**：
  - **滑动窗口**：保留最近 N 轮对话，丢弃更早的内容。
  - **摘要压缩**：用 LLM 对早期对话生成摘要，替代原文存入上下文，节省 token。
  - **关键信息提取**：从对话中抽取实体、关系、待办事项等结构化信息，保持精简。

**2. 长期记忆（Long-term Memory）**
- **本质**：跨会话持久化存储，模拟人类的"长期知识"。
- **存储方案**：

| 存储方案 | 适用数据类型 | 检索方式 | 代表工具 |
|---------|------------|---------|---------|
| 向量数据库 | 非结构化文本 | 语义相似度搜索 | Milvus, Pinecone, Weaviate, Chroma |
| 知识图谱 | 结构化实体关系 | 图查询（Cypher/SPARQL） | Neo4j, NebulaGraph |
| 关系数据库 | 结构化业务数据 | SQL 查询 | PostgreSQL, MySQL |
| Redis/缓存 | 热点数据、会话状态 | Key-Value 查询 | Redis |

- **典型流程**：
  1. **写入**：用户对话中的关键信息 → Embedding → 存入向量数据库。
  2. **检索**：新问题进来 → Embedding → 向量相似度检索 → 取出 Top-K 相关记忆 → 注入 prompt。
  3. **更新**：定期对记忆做去重、摘要、遗忘（删除过时或低质量记忆）。

**3. 工程实践要点：**
- **记忆隔离**：不同用户/会话的记忆必须隔离，通常用 `user_id` 或 `session_id` 作为分区键。
- **记忆检索质量**：Embedding 模型的选择很关键，推荐使用 BGE、GTE 或 OpenAI text-embedding-3 等高质量模型。
- **混合检索**：向量检索 + 关键词检索（BM25）的混合方案通常效果更好（即 hybrid search）。
- **记忆容量控制**：长期记忆不能无限增长，需要设置淘汰策略（如 LRU、基于时间衰减）。

> 面试加分点：可以画出你项目中的记忆架构图，说明短期/长期记忆如何配合工作，以及遇到的实际问题（如检索噪声、记忆冲突）。

## 第三部分：Tool Use 工具调用

**Q5: Tool Use 是扩展 Agent 能力的有效途径。请解释 LLM 是如何学会调用外部 API 或工具的？（可以从 Function Calling 的角度解释）**
- 难度：⭐⭐⭐
- 岗位：通用
- 标签：#Agent #ToolUse #FunctionCalling
- 公司：所有公司（高频）

**参考答案：**

LLM 调用外部工具的核心机制是 **Function Calling**（函数调用），其本质是让 LLM 学会"生成结构化的工具调用指令"而非纯自然语言。

**Function Calling 工作流程：**

```
1. 工具注册阶段
   开发者定义工具的 JSON Schema（名称、描述、参数类型）：
   {
     "name": "get_weather",
     "description": "获取指定城市的天气信息",
     "parameters": {
       "type": "object",
       "properties": {
         "city": {"type": "string", "description": "城市名称"}
       },
       "required": ["city"]
     }
   }

2. 请求阶段
   用户消息 + 工具定义 → 发送给 LLM

3. 模型决策
   LLM 判断是否需要调用工具：
   - 不需要 → 直接返回文本回答
   - 需要 → 返回结构化的工具调用请求：
     {"name": "get_weather", "arguments": {"city": "北京"}}

4. 执行阶段
   开发者解析 LLM 返回的 JSON，调用对应的函数/API

5. 回传阶段
   将工具执行结果作为 tool message 回传给 LLM

6. 总结阶段
   LLM 基于工具返回结果，生成最终自然语言回答
```

**训练方式：**
- **监督微调（SFT）**：用 `<工具描述, 用户问题, 正确工具调用>` 的三元组数据训练模型，使其学会判断何时调用工具、如何填充参数。
- **RLHF/DPO**：进一步优化工具调用的准确率和参数质量。
- **主流模型的实现**：OpenAI GPT、Claude、Qwen 等都已原生支持 Function Calling，API 层直接提供 `tools` 参数。

**关键技术点：**
1. **工具选择**：LLM 从候选工具列表中选择最合适的工具，依赖工具描述的质量。
2. **参数填充**：LLM 从用户输入中提取参数值，需要精确理解意图。
3. **多工具调用**：复杂场景下可并行调用多个工具（parallel tool calling）。
4. **嵌套调用**：一个工具的结果可以作为下一个工具的输入参数。

> 面试加分点：说明在实际项目中，你是如何处理工具调用失败、参数格式错误、多工具编排等工程问题的。

**Q6: 有微调过 Agent 能力吗？数据集如何收集？**
- 难度：⭐⭐⭐
- 岗位：算法岗重点
- 标签：#Agent #微调 #数据集

**参考答案：**

Agent 能力的微调主要涉及工具调用、规划推理、多轮对话等能力的训练。

**1. 微调数据集收集方法：**

| 方法 | 说明 | 优缺点 |
|------|------|--------|
| 人工标注 | 标注师编写 `<指令, 工具定义, 正确调用>` 三元组 | 质量高但成本高 |
| GPT 蒸馏 | 用 GPT-4 生成工具调用数据作为训练样本 | 成本适中，质量好 |
| self-instruct | 模型自己生成指令-工具调用对，人工筛选 | 可扩展但需要质量控制 |
| 线上日志挖掘 | 从生产环境收集用户真实 query + 成功的工具调用 | 最贴合真实分布 |
| 开源数据集 | ToolBench, APIBench, ToolAlpaca 等 | 免费但可能不匹配业务场景 |

**2. 微调策略：**
- **全参数微调（Full Fine-tuning）**：效果好但资源消耗大，适合有充足 GPU 的场景。
- **LoRA / QLoRA**：冻结大部分参数，只训练低秩适配层，资源消耗大幅降低，是业界主流选择。
- **两阶段训练**：
  - 阶段一：通用工具调用能力训练（用大规模公开数据）。
  - 阶段二：领域特定工具微调（用业务数据）。

**3. 关键训练细节：**
- **工具调用格式**：统一为 JSON 结构，训练模型生成符合 Schema 的输出。
- **Negative Sample**：加入"不需要调用工具"的样本，防止模型过度调用。
- **参数约束**：通过 constrained decoding（约束解码）确保生成的参数符合类型要求。

**4. 评估指标：**
- 工具选择准确率
- 参数填充正确率
- 端到端任务完成率
- 无效调用率（误触发率）

> 面试加分点：具体说明你在微调中用的是什么基座模型、数据量多大、训练了多少 epoch、效果提升了多少百分比。

## 第四部分：框架选型

**Q7: 请比较一下两个流行的 Agent 开发框架，如 LangChain 和 LlamaIndex。它们的核心应用场景有何不同？**
- 难度：⭐⭐
- 岗位：开发岗重点
- 标签：#Agent #框架 #选型
- 公司：所有公司（通用）

**参考答案：**

**LangChain 和 LlamaIndex 的核心区别：**

| 维度 | LangChain | LlamaIndex |
|------|-----------|------------|
| **核心定位** | 通用 Agent 开发框架 | 数据索引与检索框架 |
| **设计哲学** | "瑞士军刀"——链式调用、工具编排、Agent 构建 | "数据引擎"——专注于将私有数据接入 LLM |
| **核心能力** | Chain 编排、Agent 调度、Memory 管理、Tool 集成 | 文档解析、索引构建、检索增强生成（RAG） |
| **适用场景** | 构建 Agent 工作流、多工具编排、对话系统 | 企业知识库、文档问答、RAG 系统 |
| **数据接入** | 需要自己组织数据处理管线 | 内置丰富的数据连接器（Data Connector） |
| **检索策略** | 基础检索能力 | 多种高级索引（向量、树状、关键词、知识图谱） |
| **学习曲线** | 较陡，抽象层多 | 较平缓，概念聚焦 |
| **灵活性** | 高，适合复杂编排 | 中等，专注 RAG 场景 |

**选型建议：**
- 如果你的核心需求是 **构建一个能调用多种工具、执行复杂工作流的 Agent** → 选 **LangChain**（或 LangGraph）。
- 如果你的核心需求是 **让 LLM 基于企业私有数据回答问题** → 选 **LlamaIndex**。
- 实际项目中两者经常**搭配使用**：LlamaIndex 负责数据索引和检索，LangChain 负责 Agent 编排和工具调度。

**其他值得关注的框架：**
- **LangGraph**：LangChain 团队推出的有状态图编排框架，适合复杂 Agent 工作流。
- **CrewAI**：专注于多 Agent 协作。
- **AutoGen（Microsoft）**：多 Agent 对话框架。
- **Dify / Coze**：低代码 Agent 平台，适合快速搭建。

> 面试加分点：不要只说"用过"，要说出你在什么场景下选了哪个框架、遇到了什么问题、最终效果如何。

**Q8: 你用过哪些 Agent 框架？选型是如何选的？你最终场景的评价指标是什么？**
- 难度：⭐⭐⭐
- 岗位：开发岗重点
- 标签：#Agent #框架选型 #评估

**参考答案：**

这是一道综合性的实战题，考察的不是"背框架"，而是**选型决策能力和评估思维**。

**1. 框架选型决策框架：**

选型时通常从以下维度评估：

| 维度 | 考虑因素 |
|------|---------|
| **任务类型** | RAG 问答？工具编排？多轮对话？多 Agent 协作？ |
| **数据规模** | 数据量大且需要复杂索引 → LlamaIndex；数据简单 → LangChain 足够 |
| **性能要求** | 低延迟场景需要轻量框架或自研；高吞吐需要考虑批处理和缓存 |
| **团队技术栈** | Python 生态 → LangChain/LlamaIndex；TypeScript → 也有对应版本 |
| **维护成本** | 社区活跃度、文档质量、版本稳定性 |
| **定制需求** | 需要深度定制 → 自研框架或轻量库（如 Anthropic SDK + 自研编排层） |

**2. 我在实际项目中的选型经验：**

以客服 Agent 项目为例：
- **场景**：用户意图识别 → 调用业务 API → 生成回答
- **选了 LangChain**：因为核心需求是工具编排和对话管理
- **没用 LlamaIndex**：因为客服场景数据量小，不需要复杂索引
- **后来迁移到 LangGraph**：因为对话流程有复杂的状态转换（多分支条件判断），LangGraph 的图结构更适合

**3. 评价指标：**

| 评估维度 | 具体指标 |
|---------|---------|
| **任务完成率** | Agent 是否成功完成了用户的请求 |
| **工具调用准确率** | 是否调用了正确的工具、参数是否正确 |
| **响应延迟** | P50/P95/P99 延迟 |
| **成本** | 平均每次请求的 token 消耗 |
| **用户满意度** | 用户反馈评分（CSAT） |
| **鲁棒性** | 面对异常输入或工具故障时的表现 |
| **可维护性** | 新增工具/修改流程的开发效率 |

## 第五部分：Multi-Agent 协作

**Q9: 什么是多智能体系统？让多个 LLM Agent 协同工作相比于单个 Agent 有什么优势？又会引入哪些新的复杂性？**
- 难度：⭐⭐⭐⭐
- 岗位：通用
- 标签：#MultiAgent #协作 #系统设计
- 公司：字节、阿里（高频）

**参考答案：**

**多智能体系统（Multi-Agent System, MAS）** 是由多个具有独立决策能力的 Agent 组成的协作系统，各 Agent 分工合作完成单个 Agent 难以处理的复杂任务。

**相比单 Agent 的优势：**

1. **专业化分工**：每个 Agent 专注于特定领域（如搜索 Agent、代码 Agent、分析 Agent），类比人类团队中不同角色的专家。
2. **并行处理**：多个 Agent 可以并行执行子任务，显著减少总完成时间。
3. **鲁棒性提升**：单个 Agent 出错不会导致整个系统失败，其他 Agent 可以补偿或纠正。
4. **可扩展性**：新增能力只需添加新 Agent，无需修改现有 Agent。
5. **交叉验证**：多个 Agent 的结果可以互相验证，提高输出质量（如 Debate 机制）。

**引入的新复杂性：**

1. **通信开销**：Agent 之间的信息传递需要设计高效的通信协议，信息传递不当会导致信息丢失或冗余。
2. **任务分配**：如何将总任务合理拆分并分配给各 Agent？分配不当会导致负载不均或结果冲突。
3. **一致性保证**：多个 Agent 可能在某些决策上产生冲突，需要冲突解决机制。
4. **调试困难**：多 Agent 系统的行为更难预测和调试，错误传播链路更复杂。
5. **成本问题**：每个 Agent 都需要 LLM 调用，总 token 消耗成倍增加。
6. **延迟叠加**：串行 Agent 调用会导致延迟累加。

**主流多 Agent 协作模式：**

| 模式 | 说明 | 示例框架 |
|------|------|---------|
| **Pipeline** | Agent 串行处理，前一个的输出是后一个的输入 | 简单链式工作流 |
| **Router** | 一个调度 Agent 根据意图分发到不同专业 Agent | 客服路由系统 |
| **Debate** | 多个 Agent 对同一问题进行辩论，由裁判 Agent 综合结论 | 决策优化 |
| **Hierarchical** | 分层管理，上层 Agent 负责规划调度，下层 Agent 执行 | 企业级编排 |
| **Peer-to-Peer** | Agent 之间平等协作，自主协商 | AutoGen 的群聊模式 |

> 面试加分点：结合具体项目说明你用了哪种多 Agent 模式，以及为什么选择这种模式。

**Q10: 了解 A2A 框架吗？它和普通 Agent 框架的区别在哪，挑一个最关键的不同点说明。**
- 难度：⭐⭐⭐
- 岗位：算法岗重点
- 标签：#Agent #A2A #前沿技术

**参考答案：**

**A2A（Agent-to-Agent）** 是 Google 于 2025 年提出的一个开放协议，旨在解决不同平台/框架的 Agent 之间的**互操作性**问题。

**A2A 与普通 Agent 框架最关键的不同点：**

> **普通 Agent 框架解决的是"一个团队内部怎么协作"，A2A 解决的是"不同团队之间怎么对话"。**

具体来说：

| 维度 | 普通 Agent 框架（LangChain/CrewAI） | A2A 协议 |
|------|--------------------------------------|----------|
| **边界** | 框架内部 Agent 协作 | 跨框架、跨平台的 Agent 互操作 |
| **通信** | 通过代码级别的函数调用/消息传递 | 通过标准化的 HTTP + JSON-RPC 协议 |
| **发现机制** | 硬编码或配置文件 | Agent Card（标准化能力描述文件） |
| **协议层** | 应用层内部实现 | 独立的开源协议层 |
| **类比** | 同一公司的内部协作系统 | 不同公司之间的标准化接口（如 HTTP/SMTP） |

**A2A 的核心概念：**
1. **Agent Card**：JSON 格式的 Agent 能力描述，类似 OpenAPI 的 Swagger，让其他 Agent 知道"我能做什么"。
2. **Task**：A2A 将交互抽象为"任务"，一个 Agent 向另一个 Agent 发送任务请求。
3. **消息与Artifact**：任务执行过程中的通信单元和最终产出物。

**实际意义：**
- 以前 LangChain 的 Agent 和 CrewAI 的 Agent 无法直接对话，A2A 提供了统一的通信标准。
- 类比互联网发展史：A2A 对 Agent 的意义 ≈ HTTP 对 Web 的意义——标准化通信协议。

> 面试加分点：可以将 A2A 与 MCP（Model Context Protocol, Anthropic 提出）对比讨论，MCP 侧重 Agent 与工具的交互，A2A 侧重 Agent 与 Agent 的交互。

## 第六部分：挑战与优化

**Q11: 在构建一个复杂的 Agent 时，你认为最主要的挑战是什么？**
- 难度：⭐⭐⭐
- 岗位：通用
- 标签：#Agent #挑战 #优化

**参考答案：**

构建复杂 Agent 的主要挑战可以从**算法层面**和**工程层面**两个维度来回答：

**算法层面：**
1. **幻觉问题**：LLM 可能生成不存在的工具名称、错误的参数值或虚假的推理链，导致 Agent 执行错误操作。
2. **长程规划能力不足**：面对需要多步骤、长链条的任务，LLM 容易"忘记"最初目标或中途偏离。
3. **工具选择准确率**：当可用工具数量增多（如几十个 API），LLM 选择正确工具的准确率会显著下降。
4. **上下文窗口限制**：复杂任务需要大量中间信息（历史对话、工具返回、规划步骤），容易超出上下文长度。
5. **对齐与安全**：Agent 的行为可能偏离人类意图，产生有害输出或执行危险操作。

**工程层面：**
1. **延迟问题**：Agent 的多轮"思考-行动-观察"循环导致端到端延迟高，影响用户体验。
2. **成本控制**：每次推理都消耗 token，复杂 Agent 一个任务可能触发 10+ 次 LLM 调用。
3. **错误传播**：上游步骤的错误会级联放大，导致最终结果完全偏离。
4. **可观测性差**：Agent 的决策过程像一个黑盒，难以定位"为什么做了这个决定"。
5. **并发与状态管理**：多用户并发使用时，Agent 的状态隔离和资源管理是工程难题。
6. **测试与评估**：Agent 的行为具有不确定性，传统的单元测试难以覆盖，需要新的评估方法。

**我的实践经验：**
- 针对幻觉：引入工具调用的 schema 校验 + 执行结果校验。
- 针对延迟：缓存常用工具结果、并行调用独立工具、使用更小的模型做简单判断。
- 针对成本：分级路由——简单任务用小模型，复杂任务才调大模型。

> 面试加分点：不要泛泛而谈，要结合你实际遇到的最大挑战和解决方案来回答。

**Q12: 当一个 Agent 需要在真实或模拟环境中（如机器人、游戏）执行任务时，它与纯粹基于软件工具的 Agent 有什么本质区别？**
- 难度：⭐⭐⭐
- 岗位：算法岗重点
- 标签：#Agent #具身智能 #机器人

**参考答案：**

具身智能 Agent（Embodied Agent）与纯软件 Agent 的本质区别在于**与物理世界的交互方式**。

**核心区别：**

| 维度 | 纯软件 Agent | 具身智能 Agent |
|------|------------|---------------|
| **环境** | 数字环境（API、数据库、网页） | 物理或模拟环境（真实世界、3D 仿真） |
| **感知** | 文本、API 返回、结构化数据 | 多模态传感器（视觉、触觉、深度、IMU） |
| **行动** | API 调用、代码执行、消息发送 | 物理动作（移动、抓取、操作物体） |
| **错误代价** | 低——可以回滚、重试 | 高——错误动作可能造成物理损害 |
| **反馈延迟** | 毫秒-秒级 | 秒-分钟级（物理动作执行时间） |
| **状态空间** | 离散、可枚举 | 连续、高维、部分可观察 |
| **不确定性** | 主要是信息不确定性 | 信息不确定性 + 物理不确定性（摩擦、碰撞） |

**具身智能 Agent 的关键技术：**

1. **多模态感知**：需要同时处理视觉（摄像头）、深度（LiDAR）、力反馈等信号，通常使用 Vision-Language-Action（VLA）模型。
2. **动作空间建模**：将 LLM 的离散语言输出映射到连续的物理动作空间（如机器人关节角度）。
3. **仿真训练**：在 Isaac Gym、MuJoCo 等物理仿真环境中训练，再迁移到真实世界（Sim-to-Real Transfer）。
4. **安全约束**：物理动作必须有安全边界，如力矩限制、碰撞检测、紧急停止机制。
5. **实时性要求**：物理环境不等人，推理延迟必须满足控制频率要求（通常 10-100Hz）。

**代表性工作：**
- RT-2（Google）：Vision-Language-Action 模型，LLM 直接输出机器人动作。
- SayCan（Google）：LLM 做高层规划，底层动作由预训练的技能策略执行。
- Voyager（NVIDIA）：在 Minecraft 中自主探索的具身 Agent。

> 面试加分点：如果有具身智能相关项目经验，重点描述感知-决策-执行的完整链路。

**Q13: 如何确保一个 Agent 的行为是安全、可控且符合人类意图的？在 Agent 的设计中，有哪些保障对齐方法？**
- 难度：⭐⭐⭐⭐
- 岗位：通用
- 标签：#Agent #安全性 #对齐
- 公司：字节、阿里、腾讯（重要）

**参考答案：**

确保 Agent 行为安全、可控且符合人类意图，需要从**算法层面**和**系统层面**两个维度进行保障：

**一、对齐方法（Alignment）**

| 方法 | 说明 | 阶段 |
|------|------|------|
| **SFT（监督微调）** | 用高质量人类示范数据训练，让模型学会"正确行为" | 训练阶段 |
| **RLHF** | 人类反馈的强化学习，训练 Reward Model 引导模型优化 | 训练阶段 |
| **DPO** | 直接偏好优化，无需 Reward Model，更稳定 | 训练阶段 |
| **Constitutional AI** | 用一组"宪法原则"指导模型自我改进（Anthropic 提出） | 训练阶段 |

**二、推理阶段的安全保障**

1. **System Prompt 约束**：
   - 明确定义 Agent 的角色边界和禁止行为。
   - 例如："你不能执行任何涉及数据库删除的操作"。

2. **输入过滤（Guardrails）**：
   - 在用户输入到达 LLM 之前，用分类模型检测并拦截恶意指令（如越狱攻击、Prompt Injection）。
   - 工具：NeMo Guardrails、Lakera Guard、自研规则引擎。

3. **输出审查**：
   - LLM 输出后、执行前，对生成内容进行安全检查（是否包含敏感信息、是否越权）。
   - 对工具调用参数做 Schema 校验和权限校验。

4. **工具权限控制**：
   - 为每个工具设置权限等级，Agent 只能调用其权限范围内的工具。
   - 敏感操作（如支付、删除）需要人类确认（Human-in-the-Loop）。

5. **审计日志**：
   - 记录 Agent 的每一步决策和操作，支持事后追溯和分析。
   - 对异常行为设置告警。

**三、系统层面的保障**

1. **沙箱执行**：Agent 的工具调用在沙箱环境中执行，防止对生产环境的直接损害。
2. **速率限制**：限制 Agent 的操作频率，防止失控时造成大规模影响。
3. **人工接管**：当 Agent 置信度低于阈值或触发安全规则时，自动转人工处理。
4. **红队测试（Red Teaming）**：上线前进行对抗性测试，模拟各种攻击场景。

**四、Prompt Injection 防御**

这是 Agent 安全面临的独特威胁：
- **间接注入**：恶意内容藏在工具返回的数据中（如网页、邮件）。
- **防御策略**：对工具返回内容做清洗、在 prompt 中明确标识数据来源、使用单独的 LLM 做意图校验。

> 面试加分点：结合你项目中的实际安全措施来回答，并说明你遇到过哪些安全事件及处理方式。

**Q14: 在 RAG+知识图谱的 Agent 系统中，知识图谱更新的机制是怎样的？是怎样保证实时性的？**

- 岗位：算法岗重点
- 标签：#知识图谱 #实时更新
- 公司：字节(真题)

**参考答案：**

知识图谱在 RAG+Agent 系统中的更新需要保证**准确性**和**实时性**，核心机制如下：

**1. 知识图谱更新流程：**

```
数据源（文档/API/数据库）
    ↓
信息抽取（NER + 关系抽取）
    ↓
实体对齐与消歧
    ↓
知识融合（与现有图谱合并）
    ↓
质量校验（一致性检查）
    ↓
图谱更新（增量写入）
```

**2. 保证实时性的策略：**

| 策略 | 说明 |
|------|------|
| **增量更新** | 不重建整个图谱，只处理变化的部分，降低更新延迟 |
| **事件驱动** | 监听数据源变更事件（如数据库 CDC），触发图谱更新 |
| **流式处理** | 用 Kafka/Flink 等流处理框架，实时处理数据变更 |
| **版本管理** | 图谱支持版本快照，可以回溯到任意时间点 |
| **双写机制** | 向量数据库和知识图谱同步更新，保证检索一致性 |

**3. 在 RAG+Agent 中的应用：**
- **检索阶段**：用户 query → 实体识别 → 图谱查询获取关联实体和关系 → 向量检索获取相关文档 → 融合排序。
- **推理阶段**：Agent 利用图谱的结构化知识进行多跳推理，比纯向量检索更精准。
- **更新触发**：Agent 在对话中发现知识过期 → 触发图谱更新流程。

**4. 关键技术点：**
- **实体对齐**：新抽取的实体需要与图谱中已有实体匹配，避免重复节点。
- **冲突解决**：新旧知识冲突时，需要有策略（如时间戳优先、来源可信度优先）。
- **图谱质量监控**：定期运行一致性检查、孤立节点检测等质量保障任务。

**Q15: 训练 LoRA 模型时，你是如何选择冻结层的？依据是什么？**
- 难度：⭐⭐⭐
- 岗位：算法岗重点
- 标签：#LoRA #层选择
- 公司：字节(真题)

**参考答案：**

LoRA 冻结层的选择是一个重要的工程决策，影响微调效果和效率。

**1. LoRA 基本原理回顾：**
- LoRA（Low-Rank Adaptation）冻结预训练模型的全部参数，在特定层旁添加低秩矩阵 A 和 B（ΔW = BA）。
- 训练时只更新 A 和 B，参数量仅为原模型的 0.1%-1%。

**2. 冻结层选择策略：**

| 策略 | 做法 | 适用场景 |
|------|------|---------|
| **全层 LoRA** | 在所有 Transformer 层添加 LoRA | 效果最好，资源充足时首选 |
| **上层 LoRA** | 只在最后 N 层添加 LoRA | 轻量微调，保留底层通用能力 |
| **注意力层 LoRA** | 只在 Q、K、V 投影矩阵添加 LoRA | 最常见做法，性价比高 |
| **FFN 层 LoRA** | 在前馈网络层添加 LoRA | 适合需要修改知识表征的任务 |
| **选择性层 LoRA** | 根据层重要性分析选择性添加 | 资源受限时的精细策略 |

**3. 选择依据：**

- **任务相似度**：如果微调任务与预训练任务相似（如通用对话 → 客服对话），只需调整上层；差异大则需要更多层。
- **数据量**：数据少（<1000 条）→ 少层 LoRA 防过拟合；数据多 → 可以加更多层。
- **资源预算**：GPU 显存有限 → 减少 LoRA 层数或降低秩 r。
- **经验法则**：
  - 秩 r 通常选 8、16、32，从 16 开始调。
  - 目标模块推荐 `["q_proj", "v_proj"]` 或 `["q_proj", "k_proj", "v_proj", "o_proj"]`。
  - Alpha 通常设为 2×r。

**4. 实验方法：**
- 用小数据集做消融实验，比较不同层组合的效果。
- 监控训练 loss 和验证集指标，防止过拟合。
- 可以用 LoRA 的合并权重后的模型做评估。

> 面试加分点：说出你实际用的 rank、alpha、target_modules 参数，以及做过哪些对比实验。

**Q16: 大规模 Agent 系统在多线程/多进程场景下的资源调度策略如何设计？**
- 难度：⭐⭐⭐⭐
- 岗位：开发岗重点
- 标签：#资源调度 #并发
- 公司：字节(真题)

**参考答案：**

大规模 Agent 系统的并发资源调度是一个典型的系统工程问题，需要从多个层面设计：

**1. 整体架构：**

```
用户请求 → 负载均衡层
    ↓
API Gateway（限流、路由）
    ↓
Agent 调度器（任务队列 + 优先级管理）
    ↓
Worker Pool（多线程/多进程执行引擎）
    ↓
LLM 推理服务 + 工具执行服务
```

**2. 多线程 vs 多进程选择：**

| 维度 | 多线程 | 多进程 |
|------|--------|--------|
| 适用场景 | I/O 密集（等 API 响应） | CPU 密集（数据处理） |
| Python 特殊考虑 | GIL 限制，CPU 密集型无效 | 绕过 GIL，真正并行 |
| Agent 场景 | 网络调用为主，多线程足够 | 本地模型推理时用多进程 |
| 内存开销 | 共享内存，开销小 | 独立内存空间，开销大 |

**3. 调度策略设计：**

- **优先级队列**：高优先级任务（如付费用户）优先调度，低优先级任务排队。
- **资源池化**：LLM 推理资源池、工具执行资源池独立管理，按需分配。
- **动态扩缩容**：根据队列深度自动扩展 Worker 数量（K8s HPA）。
- **超时与降级**：每个任务设置超时时间，超时后降级处理（返回缓存结果或默认回答）。
- **背压机制**：当系统负载过高时，主动拒绝新请求或降低服务质量，防止雪崩。

**4. 关键技术：**
- **异步框架**：使用 asyncio/aiohttp 实现非阻塞 I/O，单线程即可处理大量并发。
- **消息队列**：用 Redis/RabbitMQ/Kafka 做任务队列，解耦调度和执行。
- **连接池**：复用 HTTP 连接和数据库连接，减少连接建立开销。
- **协程级并发**：Python 中用 `asyncio.gather()` 并行调用多个工具。

**Q17: 如果你要在 GPU 资源有限的条件下同时提供推理和微调服务，如何做资源分配和任务调度以保证时延和吞吐？**
- 难度：⭐⭐⭐⭐
- 岗位：开发岗重点
- 标签：#资源管理 #调度策略
- 公司：字节(真题)

**参考答案：**

GPU 资源有限时同时提供推理和微调服务，核心矛盾是**吞吐与时延的权衡**。

**1. 资源分配策略：**

| 策略 | 做法 | 优缺点 |
|------|------|--------|
| **时间分片** | 推理和微调交替使用 GPU（如推理白天、微调夜间） | 简单但资源利用率低 |
| **空间分片** | GPU 划分为多个分区，推理和微调各占一部分 | 需要硬件支持（MIG） |
| **优先级抢占** | 推理优先，空闲时自动启动微调任务 | 最大化利用率，推理不受影响 |
| **异构硬件** | 推理用小 GPU/TPU，微调用大 GPU | 需要多种硬件资源 |

**2. 推荐方案（优先级抢占 + 动态调度）：**

```
┌─────────────────────────────────────────┐
│             GPU 资源池                    │
│  ┌──────────────┐  ┌──────────────────┐  │
│  │ 推理服务（常驻）│  │ 微调任务（弹性）  │  │
│  │ 70% GPU       │  │ 30% GPU（空闲时  │  │
│  │ 保证低延迟     │  │ 可扩到 100%）    │  │
│  └──────────────┘  └──────────────────┘  │
└─────────────────────────────────────────┘
```

- 推理服务常驻，分配固定 GPU（如 70%），保证 P99 延迟。
- 微调任务使用剩余 GPU，推理低峰期可动态扩容。
- 用 Kubernetes + GPU Operator 管理 GPU 资源调度。

**3. 时延保障措施：**
- **推理批处理**：动态 batching（如 vLLM 的 continuous batching），提高吞吐同时控制延迟。
- **量化推理**：INT8/INT4 量化减少显存占用，加速推理。
- **KV Cache 优化**：PagedAttention（vLLM）减少显存碎片，支持更多并发。
- **请求预热**：模型预加载到 GPU，消除冷启动延迟。

**4. 吞吐优化措施：**
- **微调队列**：微调任务排入队列，根据 GPU 空闲情况动态调度。
- **梯度累积**：微调时用小 batch size + 梯度累积模拟大 batch size，减少显存占用。
- **LoRA 热切换**：微调完成后，新 LoRA 权重热加载到推理服务，无需重启。

```python
        plan = self.planner.run(
            f"请将以下旅行需求拆解为子任务：{user_request}"

        # Step 2: 并行执行独立子任务
        results = parallel_run([

        # Step 3: 规划 Agent 汇总
```

**Q19: 如果一个agent误判导致策略冲突，如何处理？**
- 难度：⭐⭐⭐
- 岗位：通用
- 标签：#错误处理 #容错机制
- 公司：字节(真题)

**参考答案：**

Agent 误判导致策略冲突时的处理，需要建立**多层防护机制**：

**1. 检测机制：**
- **输出校验**：每次 Agent 做出决策后，用规则引擎或另一个 LLM 验证决策的合理性。
- **冲突检测**：维护一个策略状态表，检测新决策是否与已有策略矛盾。
- **置信度评估**：让 Agent 输出置信度分数，低于阈值时触发人工审核。

**2. 处理策略：**

| 策略 | 做法 | 适用场景 |
|------|------|---------|
| **回滚** | 撤销错误决策，恢复到上一个安全状态 | 决策可逆时 |
| **降级** | 放弃自动化，转人工处理 | 高风险场景 |
| **重新规划** | 将冲突信息反馈给 Agent，重新生成决策 | 一般场景 |
| **规则覆盖** | 预设硬规则，Agent 决策不能违反 | 安全关键场景 |
| **投票机制** | 多个 Agent 投票，少数服从多数 | 多 Agent 系统 |

**3. 限制次数（防死循环）：**
```python
MAX_RETRIES = 3
for attempt in range(MAX_RETRIES):
    decision = agent.decide(context)
    if validate(decision):  # 校验通过
        return decision
    else:
        # 将错误信息反馈给 Agent
        context += f"\n[WARNING] 上一次决策被拒绝：{get_error_msg(decision)}"

# 超过重试次数，降级处理
return fallback_strategy()  # 人工接管或返回默认安全策略
```

**4. 反思机制（Reflexion）：**
- 当 Agent 被告知决策错误时，不是简单重试，而是先"反思"：
  - 为什么之前的决策是错的？
  - 哪些信息被忽略了？
  - 新的策略应该考虑什么？
- 将反思结果作为额外上下文注入下一次决策。

**5. 预防措施：**
- 在 system prompt 中明确列出禁止行为和优先级规则。
- 对高风险操作设置人类确认环节（Human-in-the-Loop）。
- 建立策略冲突的知识库，历史上出现过的冲突类型作为参考案例。

Agent 记忆系统的设计需要兼顾**存储效率**和**查询性能**：

**1. 分层记忆架构：**

```
┌────────────────────────────────────────────┐
│               Working Memory               │
│         当前对话上下文（内存中）              │
```

**2. 长期记忆存储方案：**

| **索引优化** | 使用 HNSW/IVF-PQ 等近似最近邻索引，亿级数据毫秒级检索 |
| **分区存储** | 按用户/时间分区，减少单次检索的数据量 |
| **定期压缩** | 将多条相似记忆合并为摘要，减少存储和检索噪声 |
| **热度缓存** | 热点用户/频繁访问的记忆放入 Redis 缓存 |
| **预计算** | 对常见 query 预计算结果并缓存 |
| **Embedding 优化** | 使用更小的 Embedding 模型（如 Matryoshka 维度压缩） |


- 百万-千万级：需要分布式向量库（Milvus 集群）。
- 亿级以上：需要分片 + 多级索引 + 缓存。

**Q21: 有没有做记忆衰退，避免旧数据干扰新任务？**
- 难度：⭐⭐⭐
- 岗位：算法岗重点
- 标签：#记忆管理 #遗忘机制
- 公司：字节(真题)

**参考答案：**

记忆衰退是防止旧数据干扰新任务的重要机制，模拟人类的遗忘过程。

**1. 为什么需要记忆衰退：**
- 用户的偏好和需求会随时间变化（如从喜欢经济舱变为偏好商务舱）。
- 过时的记忆可能产生误导（如半年前的产品价格）。
- 记忆无限增长会降低检索质量和增加存储成本。

**2. 记忆衰退的实现方式：**

**方案一：时间衰减权重**
```python
import math

def memory_score(recency, relevance, importance):
    """综合评分 = 相关性 × 重要性 × 时间衰减因子"""
    decay = math.exp(-0.1 * recency)  # recency 为距今天数
    return relevance * importance * decay
```
- 越久远的记忆，评分越低。
- 但高重要性（如用户明确偏好）的记忆衰减更慢。

**方案二：基于访问频率**
- 经常被检索到的记忆权重升高（类似 LRU 但相反——频繁访问=更有价值）。
- 长期未被检索的记忆逐渐降低优先级。

**方案三：显式过期机制**
- 为不同类型的记忆设置 TTL（Time To Live）：
  - 对话上下文：30 分钟
  - 用户偏好：30 天
  - 事实知识：永久（除非被更新）

**方案四：定期合并与摘要**
- 定期将短期记忆合并为长期摘要，原文删除。
- 如："用户在3月、4月、5月都问了北京天气" → 合并为"用户经常出差北京"。

**3. 我的实践经验：**
- 用**时间衰减 + 重要性加权**的混合方案。
- 每次检索时动态计算记忆分数，而非定期批量处理（避免延迟）。
- 重要记忆（用户主动提供的偏好）衰减系数设为普通记忆的 1/10。
- 设置最低分数阈值，低于阈值的记忆在检索时被过滤。

**4. 需要注意的边界情况：**
- 不能过度遗忘——用户的长期偏好不应轻易丢失。
- 矛盾记忆的处理：新记忆与旧记忆冲突时，以新记忆为准，旧记忆标记为"已过时"。

> 面试加分点：说明你的衰减函数是如何设计的，参数如何调优，以及如何评估记忆衰退的效果。

**方案一：Prompt 内学习（In-context Learning）**
- 将用户反馈直接拼入当前或下一轮对话的上下文中。
- 例如：`[用户纠正：我要的是北京]` → Agent 在后续对话中记住这个偏好。
- 优点：即时生效；缺点：不持久，新会话丢失。

**方案二：存入记忆系统**
- 将反馈转化为结构化记忆存入长期记忆（向量数据库）。
- 下次对话时检索相关记忆，注入 prompt。
- 优点：跨会话持久化；缺点：检索可能不准。

**方案三：离线数据积累 → 微调**
- 收集大量反馈数据（偏好对：<好回答, 差回答>）。
- 定期用 DPO/RLHF 微调模型。
- 优点：从根本上提升模型能力；缺点：周期长、成本高。

**3. 是否用 RL 进行策略更新：**

- **工业界主流做法**：大多数 Agent 系统**不用在线 RL**，而是：
  - 线上用 Prompt + 记忆系统即时响应用户反馈。
  - 线下积累数据，定期用 DPO/RLHF 微调基座模型。
- **学术前沿**：一些研究尝试在线 RL（如 RLHF on the fly），但工程复杂度高，稳定性难以保证。
- **原因**：在线 RL 有以下风险——
  - 灾难性遗忘（新反馈导致旧能力退化）。
  - 奖励欺骗（Reward Hacking）。
  - 训练不稳定。

> 面试加分点：诚实回答——如果你的项目没有用在线 RL，可以说"我们用的是离线数据积累 + 定期微调的方式"，然后解释为什么这样更合适。

**Q24: 你怎么处理响应速度与推理精度之间的tradeoff？是先召回再精排，还是单次生成？**
- 难度：⭐⭐⭐
- 岗位：通用
- 标签：#性能优化 #权衡
- 公司：字节(真题)

**参考答案：**

响应速度与推理精度的 tradeoff 是 Agent 系统设计中的核心矛盾。

**1. 两种主流策略对比：**

| 策略 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| **先召回再精排** | 先用小模型快速检索候选，再用大模型精排 | 兼顾速度和质量 | 需要两阶段设计 |
| **单次生成** | 直接用大模型一次性生成答案 | 架构简单 | 延迟高，或质量差（用小模型时） |

**2. 实际项目中的分层策略：**

```
用户 Query
    ↓
┌──────────────────┐
│  意图分类（小模型）│ ← 判断任务复杂度（<100ms）
└────────┬─────────┘
         ↓
    ┌────┴────┐
    ↓         ↓
  简单任务   复杂任务
    ↓         ↓
 小模型      大模型
 直接回答    RAG 流程
（<500ms）  （2-5s）
```

**3. 具体优化手段：**

**速度优化：**
- **模型分级**：简单任务用小模型（Claude Haiku / Qwen-7B），复杂任务用大模型。
- **缓存**：语义缓存——相似 query 直接返回缓存结果（用 Embedding 相似度判断）。
- **流式输出**：SSE（Server-Sent Events）让用户先看到部分结果，降低感知延迟。
- **并行调用**：多个工具同时调用，而非串行等待。
- **Speculative Decoding**：小模型推测，大模型验证，加速推理。

**精度优化：**
- **RAG 流程**：Retrieve → Rerank → Generate，确保 LLM 基于真实数据回答。
- **多次验证**：对关键输出用另一个 LLM 交叉验证。
- **Self-Consistency**：多次采样取投票结果，提高输出稳定性。
- **CoT 强制**：要求模型先输出推理过程再给结论，提高准确率。

**4. 我的实践经验：**
- 对于客服场景：采用"先召回再精排"策略。
  - 第一阶段：Embedding 检索 Top-20 相关文档（<50ms）。
  - 第二阶段：Cross-Encoder 精排 Top-5（<200ms）。
  - 第三阶段：LLM 基于精排结果生成答案（<1s）。
  - 总延迟控制在 1.5s 以内，准确率 92%+。

**Q27: 构建 Agent 的时候，遇到过哪些瓶颈？LangChain 的 memory 默认机制在多用户并发中怎么做隔离？你是如何保证线程安全的？**
- 难度：⭐⭐⭐
- 岗位：开发岗重点
- 标签：#工程实践 #并发安全
- 公司：字节(真题)

**参考答案：**

LangChain 的 Memory 默认机制在多用户并发场景下确实有线程安全问题，这是实际项目中的常见坑。

**1. 问题分析：**

- LangChain 的 `ConversationBufferMemory` 和 `ConversationSummaryMemory` 默认是**有状态的实例对象**。
- 如果多个用户共享同一个 Memory 实例，会出现：
  - 用户 A 看到用户 B 的对话内容（数据泄露）。
  - 对话历史混乱（状态串扰）。

**2. 解决方案：**

**方案一：每会话独立实例（推荐）**
```python
# 每个用户/会话创建独立的 Memory 实例
class AgentService:
    def get_agent(self, session_id: str):
        memory = self.load_memory(session_id)  # 从 Redis/DB 加载
        agent = Agent(memory=memory)
        return agent
```

**方案二：自定义 Memory 后端**
```python
from langchain.memory import ConversationBufferMemory

class RedisBackedMemory(ConversationBufferMemory):
    """用 Redis 做持久化后端，天然支持按 key 隔离"""

    def __init__(self, session_id: str, redis_client):
        super().__init__()
        self.session_id = session_id
        self.redis = redis_client

    def save_context(self, inputs, outputs):
        # 按 session_id 隔离存储
        key = f"memory:{self.session_id}"
        self.redis.rpush(key, json.dumps({"input": inputs, "output": outputs}))
```

**方案三：无状态设计（最安全）**
```python
# 不依赖 LangChain 的 Memory，自行管理状态
def chat(session_id, user_message):
    # 1. 从 Redis 加载历史
    history = redis.lrange(f"chat:{session_id}", 0, -1)

    # 2. 拼接上下文
    messages = load_history(history) + [{"role": "user", "content": user_message}]

    # 3. 调用 LLM
    response = llm.chat(messages)

    # 4. 保存新消息
    redis.rpush(f"chat:{session_id}", json.dumps({"role": "user", "content": user_message}))
    redis.rpush(f"chat:{session_id}", json.dumps({"role": "assistant", "content": response}))

    return response
```

**3. 线程安全最佳实践：**
- **不要用全局变量**存储 Agent 状态。
- **用 Redis/数据库**做状态存储，利用其天然的并发安全特性。
- **每个请求独立创建** Agent/Memory 实例（开销很小，因为不涉及模型加载）。
- **注意连接池**：复用 Redis/DB 连接，但不要复用 Memory 对象。

**4. 实际项目中的瓶颈：**
- **Token 消耗**：长对话历史消耗大量 token → 用摘要压缩解决。
- **并发瓶颈**：高并发时 Redis 连接数成为瓶颈 → 用连接池 + 集群。
- **冷启动**：加载历史对话有延迟 → 异步预加载。

**Q28: 你做的 Agent 使用了多少个外部工具，在调用链条上如何保障故障容错和超时机制？**
- 难度：⭐⭐⭐
- 岗位：开发岗重点
- 标签：#工具调用 #容错设计
- 公司：字节(真题)

**参考答案：**

工具调用链路的故障容错和超时机制是 Agent 系统的**生产级必备能力**。

**1. 调用链路架构：**

```
Agent 决策 → 工具路由 → 参数校验 → 执行引擎 → 结果校验 → 返回 Agent
                          ↑            ↑            ↑
                       Schema检查   超时/重试    格式校验
```

**2. 故障容错设计：**

| 层级 | 容错措施 | 具体实现 |
|------|---------|---------|
| **参数层** | Schema 校验 | 检查参数类型、必填项、取值范围 |
| **网络层** | 超时 + 重试 | 设置连接超时和读取超时，指数退避重试 |
| **服务层** | 熔断器 | 连续失败 N 次后熔断，一段时间后半开试探 |
| **数据层** | 结果校验 | 检查返回数据格式、字段完整性 |
| **系统层** | 降级策略 | 工具不可用时切换到备用方案 |

**3. 超时机制设计：**

```python
import asyncio
from tenacity import retry, stop_after_attempt, wait_exponential

class ToolExecutor:
    def __init__(self):
        self.timeout = 10  # 默认10秒超时
        self.max_retries = 3

    @retry(stop=stop_after_attempt(3),
           wait=wait_exponential(multiplier=1, min=1, max=10))
    async def call_tool(self, tool_name, params):
        try:
            result = await asyncio.wait_for(
                self._execute(tool_name, params),
                timeout=self.timeout
            )
            return result
        except asyncio.TimeoutError:
            raise ToolTimeoutError(f"工具 {tool_name} 超时")
        except Exception as e:
            raise ToolExecutionError(f"工具 {tool_name} 执行失败: {e}")
```

**4. 调用链路保障：**

- **并行调用互不影响**：多个工具并行调用时，一个失败不影响其他，用 `asyncio.gather(return_exceptions=True)`。
- **结果缓存**：对相同参数的工具调用做短时缓存（TTL 5 分钟），减少重复调用。
- **调用链追踪**：给每次工具调用分配 trace_id，用 OpenTelemetry 做分布式追踪。
- **监控告警**：实时监控工具调用成功率、延迟 P99，异常时告警。

**5. 常见工具数量参考：**
- 简单 Agent：3-5 个工具
- 中等复杂度：10-20 个工具
- 复杂系统：30+ 个工具（需要做工具分组/分层管理）

**Q29: 有没有做过工具调用失败后的feedback策略设计？**
- 难度：⭐⭐⭐
- 岗位：算法岗、开发岗
- 标签：#错误恢复 #反馈机制
- 公司：字节(真题)

**参考答案：**

工具调用失败后的 feedback 策略是 Agent 鲁棒性的关键。

**1. 失败分类与对应策略：**

| 失败类型 | 示例 | 反馈策略 |
|---------|------|---------|
| **参数错误** | 必填参数缺失、类型不对 | 将错误信息回传 LLM，让它修正参数重新调用 |
| **超时** | API 响应超过 10 秒 | 重试（最多 2-3 次），若仍失败则降级 |
| **服务不可用** | 500 错误、连接拒绝 | 熔断，切换备用工具或返回兜底结果 |
| **业务逻辑错误** | "订单不存在"、"余额不足" | 将错误消息反馈给 LLM，生成面向用户的回答 |
| **返回格式异常** | 返回的不是预期 JSON | 尝试解析修复，或要求 LLM 重新调用 |

**2. Feedback 策略设计：**

```python
async def execute_with_feedback(agent, tool_call, max_retries=2):
    for attempt in range(max_retries + 1):
        try:
            result = await execute_tool(tool_call)

            # 校验结果
            if not validate(result):
                # 将校验错误反馈给 Agent
                feedback = f"工具返回结果格式异常：{result}，请检查调用参数"
                tool_call = agent.reflect(feedback, tool_call)
                continue

            return result

        except ToolTimeoutError:
            if attempt < max_retries:
                feedback = f"工具 {tool_call.name} 执行超时，请尝试其他方式或简化请求"
                tool_call = agent.reflect(feedback, tool_call)
            else:
                return fallback_result("抱歉，服务暂时繁忙，请稍后重试")

        except ToolError as e:
            # 将具体错误信息反馈给 Agent
            feedback = f"工具调用失败，错误信息：{e.message}"
            tool_call = agent.reflect(feedback, tool_call)

    return fallback_result("多次尝试后仍然失败")
```

**3. 降级策略：**

```
工具 A 失败 → 尝试工具 B（功能相似）
    ↓ B 也失败
尝试从缓存返回（如果之前有过相似查询）
    ↓ 缓存也没有
返回兜底回答："我暂时无法处理这个请求，已转交人工客服"
```

**4. 用户澄清机制：**
- 当错误是由于用户输入模糊导致时（如"帮我订那个"→ 工具调用缺少参数），不应直接重试，而是**主动询问用户**。
- 例如："请问您想查询哪个城市的天气？"

- 公司：字节(真题)

**参考答案：**

多轮对话上下文状态管理 + 高并发一致性是 Agent 系统的工程核心难点。

**1. 上下文状态管理：**

**需要管理哪些状态：**
- 对话历史（消息列表）
- 当前任务进度（执行到哪一步了）
- 已收集的实体信息（用户名、地址、订单号等）
- 工具调用记录（调用过什么、结果是什么）
- 对话元数据（用户 ID、会话 ID、创建时间）

**状态管理方案：**

| 方案 | 适用场景 | 一致性 | 性能 |
|------|---------|--------|------|
| **Redis** | 高频读写、需要 TTL | 强一致（单节点） | 极高 |
| **Redis + 持久化** | 需要数据不丢 | 最终一致 | 高 |
| **关系数据库** | 需要事务、复杂查询 | 强一致 | 中 |
| **本地内存 + 快照** | 单机部署 | 强一致 | 极高但不支持分布式 |

**2. 推荐架构（Redis 为主，DB 做持久化）：**

```python
class ConversationStateManager:
    def __init__(self, redis_client, db_client):
        self.redis = redis_client
        self.db = db_client

    async def get_state(self, session_id: str) -> ConversationState:
        # 优先从 Redis 读
        data = await self.redis.get(f"session:{session_id}")
        if data:
            return ConversationState.from_json(data)
        # Redis 没有则从 DB 读（冷启动）
        data = await self.db.load_session(session_id)
        if data:
            await self.redis.setex(f"session:{session_id}", 3600, data)
        return data

    async def update_state(self, session_id: str, state: ConversationState):
        # 先写 Redis
        await self.redis.setex(
            f"session:{session_id}", 3600, state.to_json()
        )
        # 异步持久化到 DB
        await self.db.save_session(session_id, state)
```

**3. 高并发一致性保障：**

| 问题 | 解决方案 |
|------|---------|
| **并发写入冲突** | 用 Redis 的 WATCH/MULTI 实现乐观锁 |
| **读写不一致** | 读写都走 Redis 主节点，从节点只做备份 |
| **分布式会话路由** | 用 sticky session 或一致性哈希，保证同一会话落到同一节点 |
| **状态过大** | 对话历史超过阈值时做摘要压缩 |
| **过期清理** | 设置 TTL + 定期清理过期会话 |

**4. 关键注意事项：**
- 对话历史不能无限增长——需要设置上限（如保留最近 20 轮）。
- 超出上下文窗口时，用摘要代替原文。
- 分布式环境下，避免使用本地内存缓存状态。

**Q32: 你是如何利用多Agent协同来提高推理正确率的？调度策略如何实现？**
- 难度：⭐⭐⭐⭐
- 岗位：算法岗重点
- 标签：#Multi-Agent #调度策略
- 公司：字节(真题)

**参考答案：**

多 Agent 协同提高推理正确率的核心思路是**交叉验证**和**专业化分工**。

**1. 协同提高正确率的策略：**

**策略一：多 Agent 投票（Ensemble Voting）**
```
同一个问题 → Agent A 回答 → 答案 A
           → Agent B 回答 → 答案 B
           → Agent C 回答 → 答案 C
                    ↓
           投票/一致性检查 → 最终答案
```
- 适用于高风险决策场景（如医疗、法律）。
- 代价：3x LLM 调用成本。

**策略二：Verifier + Generator**
```
Generator Agent → 生成初步回答
    ↓
Verifier Agent → 审查回答的正确性
    ↓（如果验证不通过）
Generator Agent → 根据反馈修正回答
    ↓（循环直到通过或超过重试次数）
```
- 用一个 Agent 生成，另一个 Agent 审查。
- 类似人类的"起草 + 审核"流程。

**策略三：专业化分工**
```
路由 Agent → 判断问题类型
    ↓
数学 Agent → 处理计算类问题（准确率更高）
代码 Agent → 处理编程类问题
常识 Agent → 处理通用问答
```
- 每个 Agent 在自己的领域更精准。

**2. 调度策略实现：**

```python
class MultiAgentScheduler:
    def __init__(self):
        self.router = Agent(role="router")
        self.experts = {
            "math": Agent(role="math_expert"),
            "code": Agent(role="code_expert"),
            "general": Agent(role="general_expert"),
        }
        self.verifier = Agent(role="verifier")

    async def run(self, query):
        # Step 1: 路由
        route = await self.router.run(f"这个问题属于哪个领域：{query}")

        # Step 2: 专家回答
        answer = await self.experts[route].run(query)

        # Step 3: 验证
        verification = await self.verifier.run(
            f"请验证以下回答是否正确：\n问题：{query}\n回答：{answer}"
        )

        if verification.is_correct:
            return answer
        else:
            # 修正后重试
            return await self.experts[route].run(
                f"验证反馈：{verification.feedback}\n请修正回答"
            )
```

**3. 效果评估：**
- 单 Agent 正确率 85% → Generator + Verifier 模式提升到 93%。
- 三 Agent 投票模式提升到 95%，但成本增加 3x。
- 需要在正确率和成本之间做权衡。

**Q33: 你做Prompt优化时，是如何判断优化后的Prompt在Agent推理链路中性能提升的？用什么指标来衡量？**
- 难度：⭐⭐⭐
- 岗位：算法岗重点
- 标签：#Prompt评估 #性能指标
- 公司：字节(真题)

**参考答案：**

Prompt 优化的效果评估需要建立**可量化的评估体系**。

**1. 评估指标：**

| 指标 | 说明 | 计算方式 |
|------|------|---------|
| **工具选择准确率** | Agent 是否选了正确的工具 | 正确次数 / 总调用次数 |
| **参数填充准确率** | 工具参数是否正确 | 正确参数数 / 总参数数 |
| **端到端任务完成率** | 是否成功完成用户请求 | 完成数 / 总请求数 |
| **推理步骤效率** | 是否用了最少步骤完成任务 | 最优步骤数 / 实际步骤数 |
| **无效率** | 无效工具调用（不该调用时调用了） | 无效调用数 / 总调用数 |
| **平均 Token 消耗** | 每次请求的 token 数 | 总 token / 请求数 |
| **延迟** | 端到端响应时间 | P50/P95/P99 |

**2. 评估方法：**

**方法一：基准测试集（Benchmark）**
- 准备 200-500 条标准测试 case（包含输入、期望工具调用、期望输出）。
- 每次 Prompt 变更后，自动跑一遍基准测试，对比各项指标。

```python
def evaluate_prompt(prompt_version, test_cases):
    results = {"tool_accuracy": 0, "task_completion": 0, "avg_tokens": 0}
    for case in test_cases:
        response = agent.run(case.input, prompt=prompt_version)
        if response.tool == case.expected_tool:
            results["tool_accuracy"] += 1
        if task_completed(response, case.expected_output):
            results["task_completion"] += 1
        results["avg_tokens"] += response.token_count

    results["tool_accuracy"] /= len(test_cases)
    results["task_completion"] /= len(test_cases)
    results["avg_tokens"] /= len(test_cases)
    return results
```

**方法二：LLM-as-Judge**
- 用 GPT-4 或 Claude 作为评委，对 Agent 输出打分。
- 适合评估开放性问题（没有标准答案的场景）。

**方法三：A/B 测试**
- 线上同时运行新旧 Prompt，对比真实用户场景下的效果。
- 关键指标：用户满意度、任务完成率、转人工率。

**3. 判断 Prompt 优化有效性的标准：**
- 工具选择准确率提升 ≥ 3%
- 任务完成率提升 ≥ 5%
- Token 消耗不增加（或增加 < 10%）
- 延迟不显著增加

**Q34: 在多Agent系统中，如何保证异步任务执行的稳定性和结果一致性？**
- 难度：⭐⭐⭐⭐
- 岗位：开发岗重点
- 标签：#异步执行 #一致性
- 公司：字节(真题)

**参考答案：**

多 Agent 系统中异步任务的稳定性和结果一致性是分布式系统的经典问题。

**1. 核心挑战：**
- Agent A 发出异步任务给 Agent B，如何知道 B 是否成功？
- 多个 Agent 并行执行任务，如何保证最终结果一致？
- 部分任务失败时，如何处理已完成的部分？

**2. 解决方案：**

**方案一：事件驱动 + 消息队列**
```
Agent A 发布任务 → 消息队列（Kafka/RabbitMQ）
                      ↓
              Agent B 消费任务
                      ↓
              执行完成后发布结果事件
                      ↓
              Agent A 订阅结果事件
```
- 消息队列保证：至少一次投递、消息持久化、消费确认。
- 幂等性：同一任务执行多次结果相同（通过 task_id 去重）。

**方案二：Saga 模式（分布式事务）**
```
Task 1: 订机票 → ✅ 成功
Task 2: 订酒店 → ❌ 失败
Compensation: 取消已订的机票（补偿操作）
```
- 每个步骤都有对应的补偿操作（撤销）。
- 保证最终一致性：要么全部成功，要么全部回滚。

**方案三：CQRS + 事件溯源**
- 将任务的每一次状态变更记录为事件。
- 通过回放事件可以重建任意时刻的状态。
- 适合需要完整审计日志的场景。

**3. 具体实现要点：**

```python
class AsyncTaskManager:
    async def execute_with_guarantee(self, tasks: list):
        # 1. 所有任务注册到状态跟踪器
        task_ids = [self.register(t) for t in tasks]

        # 2. 并行执行，设置超时
        results = await asyncio.gather(
            *[self._execute_with_timeout(t, timeout=30) for t in tasks],
            return_exceptions=True
        )

        # 3. 检查结果一致性
        succeeded = [r for r in results if not isinstance(r, Exception)]
        failed = [r for r in results if isinstance(r, Exception)]

        if failed:
            # 执行补偿操作
            await self.compensate(succeeded)
            raise AggregateError(f"{len(failed)} 个子任务失败")

        return succeeded
```

**4. 稳定性保障机制：**
- **重试**：失败任务自动重试（最多 3 次，指数退避）。
- **超时**：每个任务设置超时上限。
- **死信队列**：多次重试失败的任务进入死信队列，人工处理。
- **心跳检测**：Agent 定期发送心跳，超时未响应视为宕机。
- **幂等性**：所有操作设计为幂等，重复执行不会产生副作用。

**Q36: 如果子agent回复不对怎么办？反思？跳不出去怎么办？限制次数？**
- 难度：⭐⭐⭐
- 岗位：通用
- 标签：#错误处理 #反思机制
- 公司：字节(真题)

**参考答案：**

子 Agent 回复不对时的处理需要建立**多层级兜底机制**。

**1. 检测：怎么知道回复不对？**
- **输出校验器**：用规则或 LLM 检查回复是否合理（如事实性校验、格式校验）。
- **置信度评估**：让子 Agent 同时输出置信度分数。
- **用户反馈**：用户明确表示"不对"/"不满意"。

**2. 反思机制（Reflection）：**

```python
def handle_incorrect_response(sub_agent_response, original_task):
    # Step 1: 将错误信息反馈给子 Agent
    reflection_prompt = f"""
    你的回答被认为不正确。
    原始任务：{original_task}
    你的回答：{sub_agent_response}
    错误原因：[具体的错误说明]

    请分析为什么你的回答是错误的，然后重新回答。
    """

    new_response = sub_agent.run(reflection_prompt)
    return new_response
```

**3. 限制次数 + 防死循环：**

```python
MAX_REFLECTION_ROUNDS = 3  # 最多反思3次

for attempt in range(MAX_REFLECTION_ROUNDS):
    response = sub_agent.run(task)
    if validate(response):  # 校验通过
        return response

    # 反思：将错误信息注入上下文
    task = f"{task}\n[反思第{attempt+1}次] 之前的回答被判定为不正确，原因：{get_error(response)}"

# 超过限制次数后的策略
return switch_to_parent_agent(task)  # 交给父 Agent 处理
# 或者
return human_fallback(task)  # 转人工
```

**4. 跳不出来的处理策略：**

| 策略 | 做法 |
|------|------|
| **升级处理** | 转交给父 Agent 或更高级的 Agent 处理 |
| **切换策略** | 换一个不同的子 Agent 或不同的 prompt 策略 |
| **人工兜底** | 超过重试次数后自动转人工 |
| **降级回答** | "我暂时无法准确回答这个问题，以下是我找到的相关信息：..." |
| **默认安全回复** | 最高级别的兜底，如"请稍后重试或联系人工客服" |

**5. 设计原则：**
- 每次反思必须有**新的信息**（不能简单重试相同输入）。
- 反思轮数有**硬性上限**（推荐 2-3 次）。
- 设置**超时总时限**（如 30 秒内必须给出最终回复）。

**Q37: Agent怎么评估效果？**
- 难度：⭐⭐⭐
- 岗位：通用
- 标签：#Agent评估 #效果评价
- 公司：字节、阿里(高频)

**参考答案：**

Agent 评估是一个正在快速发展的领域，需要**多维度、多层级**的评估体系。

**1. 评估维度：**

| 维度 | 指标 | 评估方法 |
|------|------|---------|
| **准确性** | 回答正确率、工具调用准确率 | 标注测试集 + 自动化评测 |
| **完整性** | 是否完整回答了用户问题 | LLM-as-Judge / 人工评估 |
| **效率** | 推理步骤数、Token 消耗、延迟 | 自动化统计 |
| **鲁棒性** | 对异常输入的处理能力 | 对抗测试 + 边缘 case |
| **安全性** | 是否产生有害输出 | Red Teaming + 规则检测 |
| **用户体验** | 满意度评分、转人工率 | 线上 A/B 测试 |

**2. 评估方法分类：**

**方法一：基于基准测试（Benchmark）**
- 准备标注数据集（输入、期望工具调用、期望输出）。
- 自动计算准确率、召回率等指标。
- 代表性基准：ToolBench、AgentBench、WebArena。

**方法二：LLM-as-Judge**
- 用更强的模型（如 GPT-4）评价 Agent 输出的质量。
- 评分维度：正确性、完整性、相关性、安全性。
- 优点：可评估开放性任务；缺点：评判本身可能不准。

**方法三：人工评估**
- 人工对 Agent 输出进行评分（1-5 分）。
- 适合评估主观质量和用户体验。
- 通常抽检 100-200 条，覆盖各种场景。

**方法四：线上指标**
- 任务完成率（用户是否满意到结束对话）。
- 转人工率（Agent 处理不了转人工的比例）。
- 用户反馈（点赞/踩比例）。
- 会话轮数（越少越好，说明 Agent 高效）。

**3. 自动化评估流水线：**
```
评测数据集 → Agent 执行 → 收集轨迹 → 自动评分 → 生成报告
     ↓              ↓            ↓           ↓
  标注case      完整log      工具调用记录   多维度分数
```

**4. 实践建议：**
- 建立**回归测试集**：每次迭代跑一遍，确保不退化。
- 关注**Bad Case 分析**：不只看平均分，重点分析低分 case 的根因。
- 定期做**红队测试**：模拟恶意用户，测试安全边界。

> 面试加分点：说明你在项目中建立了怎样的评估体系，包括多少条测试 case、几个评估维度。

**Q38: 你简历中的客服Agent项目，是如何判断用户意图是否需要调用外部API的？用了分类模型还是prompt判断？**
- 难度：⭐⭐
- 岗位：通用
- 标签：#意图识别 #API调用
- 公司：字节(真题)

**参考答案：**

判断用户意图是否需要调用外部 API，通常有两种主流方案，实际项目中经常**结合使用**。

**1. 方案对比：**

| 方案 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| **Prompt 判断** | 让 LLM 在回答时自行决定是否调用工具 | 灵活、能理解复杂意图 | 不够稳定，可能误判 |
| **分类模型** | 先用分类模型判断意图，再决定是否调工具 | 准确率高、速度快 | 需要额外训练、灵活性差 |
| **混合方案** | 分类模型做初筛，LLM 做精细判断 | 兼顾速度和准确性 | 系统复杂度增加 |

**2. Prompt 判断方案（主流）：**

```python
# 在 system prompt 中定义规则
system_prompt = """
你是一个客服助手。你有以下工具：
- query_order: 查询订单状态
- query_logistics: 查询物流信息
- refund: 发起退款

判断规则：
- 如果用户问订单、物流、退款等需要实时数据的问题 → 调用对应工具
- 如果是闲聊、FAQ 类问题 → 直接回答，不调用工具
"""
```

- **优势**：实现简单，不需要额外模型，能处理复杂语境。
- **劣势**：对 prompt 质量依赖高，边缘 case 可能误判。

**3. 分类模型方案：**

```python
# 训练一个意图分类模型
intent_labels = ["chitchat", "query_order", "query_logistics", "refund", "faq"]

# 流程
def process(user_message):
    intent = classifier.predict(user_message)

    if intent in ["chitchat", "faq"]:
        return llm.generate(user_message)  # 直接回答
    else:
        return agent.run_with_tool(user_message, tool=intent)
```

- **优势**：延迟低（分类模型很小）、准确率高（针对性训练）。
- **劣势**：需要标注数据、新增意图需要重新训练。

**4. 推荐的混合方案：**

```
用户消息 → 分类模型初筛（<10ms）
    ↓
置信度 > 0.9？→ 直接路由
置信度 < 0.9？→ 交给 LLM 做精细判断
```

- 分类模型处理 80% 的明确 case（快且准）。
- LLM 处理 20% 的模糊 case（灵活且准确）。

> 面试加分点：说明你在项目中选了哪种方案，准确率是多少，以及如何处理误判。

**Q39: 大模型生成工具调用时，如何避免参数格式错误？有哪些后处理或约束解码方法？**
- 难度：⭐⭐⭐
- 岗位：算法岗重点
- 标签：#工具调用 #格式约束
- 公司：字节(真题)

**参考答案：**

大模型生成工具调用时参数格式错误是常见问题，需要**多层级防护**来保证输出稳定。

**1. 常见格式错误类型：**
- JSON 语法错误（缺少引号、多余逗号、括号不匹配）。
- 参数类型错误（期望 int，输出了 string）。
- 缺少必填参数。
- 参数值不在合法范围内。
- 多余的无关字段。

**2. 后处理方法：**

| 方法 | 做法 | 效果 |
|------|------|------|
| **JSON 修复** | 用正则/解析器自动修复常见语法错误 | 修复 90% 的简单语法错误 |
| **Schema 校验** | 用 JSON Schema 校验输出，定位具体错误 | 精确报错 |
| **默认值填充** | 缺少可选参数时用默认值 | 提高鲁棒性 |
| **类型强制转换** | `"123"` → `123` 自动类型转换 | 修复类型不匹配 |

```python
import json
from jsonschema import validate

def parse_tool_call(raw_output, schema):
    try:
        parsed = json.loads(raw_output)
    except json.JSONDecodeError:
        # 尝试修复：提取 JSON 部分
        parsed = extract_and_fix_json(raw_output)

    # Schema 校验
    try:
        validate(parsed, schema)
    except ValidationError as e:
        # 参数修正
        parsed = fix_params(parsed, e)

    return parsed
```

**3. 约束解码方法（更根本的解决方案）：**

| 方法 | 原理 | 适用场景 |
|------|------|---------|
| **JSON Mode** | API 层面强制输出合法 JSON | OpenAI `response_format={"type": "json_object"}` |
| **Grammar-guided Decoding** | 用语法规则约束生成过程 | llama.cpp、Outlines |
| **Constrained Decoding** | 在每个 token 选择时屏蔽非法 token | 适合工具调用场景 |
| **JSON Schema Enforcing** | 强制输出符合预定义 Schema | 某些推理框架支持 |
| **Function Calling 模式** | 模型原生支持，由 API 层处理 | OpenAI/Claude 的 tool_use |

**4. 实践建议：**
- 优先使用模型原生的 **Function Calling 能力**（而非让模型自由生成 JSON）。
- 对于不支持 Function Calling 的模型，使用 **JSON Mode + Schema 校验**。
- 在 prompt 中明确给出参数示例，减少格式歧义。
- 设置**重试机制**：格式错误时将错误信息反馈给模型，让其修正。

**5. JSON Mode vs Function Calling：**
- **JSON Mode**：只保证输出合法 JSON，不保证内容正确。
- **Function Calling**：模型专门训练过工具调用，格式和内容都更可靠。

> 面试加分点：说明你在项目中用的是什么方法，格式错误率从多少降到了多少。

**Q40: 当多个工具都能完成子任务时，你的Agent如何做选择？有没有引入打分或排序模块？**
- 难度：⭐⭐⭐
- 岗位：算法岗重点
- 标签：#工具选择 #决策机制
- 公司：字节(真题)

**参考答案：**

多工具选择问题本质上是**工具路由决策**问题。

**1. 工具选择策略：**

| 策略 | 做法 | 优缺点 |
|------|------|--------|
| **LLM 自主判断** | 在 prompt 中列出所有工具描述，让 LLM 选择 | 灵活但工具多时准确率下降 |
| **工具分组** | 先选类别，再选具体工具 | 两级路由，提高准确率 |
| **打分排序** | 用模型对候选工具打分，选最高分 | 更可控，适合工具多的场景 |
| **规则优先** | 先用规则匹配（关键词/正则），规则无法匹配时交给 LLM | 快速且准确 |

**2. 打分排序模块设计：**

```python
class ToolSelector:
    def __init__(self, tools, llm):
        self.tools = tools
        self.llm = llm

    def select(self, user_query, top_k=3):
        # Step 1: 粗筛——用 Embedding 相似度快速过滤
        query_embedding = embed(user_query)
        candidates = vector_search(query_embedding, self.tools, top_k=10)

        # Step 2: 精排——让 LLM 对候选工具打分
        scored = []
        for tool in candidates:
            score = self.llm.run(
                f"评估工具 '{tool.name}' 对以下任务的适用性（0-10分）：\n"
                f"工具描述：{tool.description}\n"
                f"用户任务：{user_query}\n"
                f"只输出分数"
            )
            scored.append((tool, int(score)))

        # Step 3: 选最高分的工具
        scored.sort(key=lambda x: x[1], reverse=True)
        return scored[0][0]
```

**3. 实际项目中的做法：**
- **工具少于 10 个**：直接让 LLM 从完整列表中选择（简单有效）。
- **工具 10-50 个**：先按类别分组，LLM 先选类别再选工具。
- **工具 50+ 个**：Embedding 检索 + LLM 精排的两阶段方案。

**4. 关键优化点：**
- **工具描述质量**：好的工具描述 = 好的选择准确率。描述要清晰说明：工具名称、功能、适用场景、参数说明。
- **Few-shot 示例**：在 prompt 中给出几个"用户问题 → 正确工具"的示例。
- **Negative 示例**：给出容易混淆的 case，教模型区分相似工具。

> 面试加分点：说明你的工具数量和选择准确率，以及如何优化工具描述。

**Q41: 在Agent中引入"记忆"机制时，为什么常用向量数据库？如何设计embedding和检索策略？**
- 难度：⭐⭐⭐
- 岗位：通用
- 标签：#记忆系统 #向量数据库
- 公司：字节、阿里(高频)

**参考答案：**

向量数据库是 Agent 记忆系统的核心基础设施，原因是它能实现**语义级别**的记忆检索。

**1. 为什么用向量数据库？**

传统存储的检索方式 vs 向量检索：

| 存储方式 | 检索方式 | 局限 |
|---------|---------|------|
| 关键词搜索（MySQL） | 精确匹配或模糊匹配 | "订机票"搜不到"预订航班" |
| 向量数据库 | 语义相似度匹配 | 理解语义，"订机票"≈"预订航班" |

Agent 的记忆需要**语义匹配**而非关键词匹配：
- 用户说"上次那个酒店"→ 需要找到之前提到的酒店，不是搜索关键词"上次那个酒店"。
- 用户说"怎么退换货"→ 需要匹配到退货政策和换货流程。

**2. Embedding 策略设计：**

| 策略 | 做法 | 适用场景 |
|------|------|---------|
| **整段 Embedding** | 一条记忆整体做一个 Embedding | 记忆片段短（<500 字） |
| **滑动窗口** | 将长文档切分为重叠片段分别 Embedding | 长文档记忆 |
| **摘要 + 原文双 Embedding** | 摘要做粗检索，原文做精排 | 兼顾召回率和精度 |
| **多粒度 Embedding** | 句子级 + 段落级 + 文档级 | 多尺度检索 |

**3. 检索策略设计：**

```
用户 Query → Embedding → 向量检索 Top-K → 重排序 → 注入 Prompt
                              ↑
                        混合检索（可选）
                    向量检索 + 关键词检索
```

**核心参数调优：**

| 参数 | 说明 | 推荐值 |
|------|------|--------|
| **chunk_size** | 文本切分长度 | 256-512 token |
| **chunk_overlap** | 切分重叠量 | chunk_size 的 10-20% |
| **top_k** | 检索返回条数 | 5-10 条 |
| **similarity_threshold** | 相似度阈值 | 0.7-0.8 |
| **index_type** | 索引类型 | HNSW（精度高）/ IVF-PQ（速度快） |

**4. 检索优化技巧：**
- **HyDE（Hypothetical Document Embedding）**：先用 LLM 生成一个假设性答案，用假设答案的 Embedding 去检索（效果提升 10-20%）。
- **Query Rewriting**：将用户的口语化 query 改写为更适合检索的形式。
- **Cross-Encoder 重排序**：向量检索后用 Cross-Encoder 精排，提高 Top-K 的精度。

> 面试加分点：说明你用的 Embedding 模型（如 BGE、GTE）、向量数据库、以及检索的 Recall@10 指标。

**Q42: 项目上线后，你是如何收集bad case并迭代模型/策略的？有做在线学习吗？**
- 难度：⭐⭐⭐
- 岗位：通用
- 标签：#迭代优化 #在线学习
- 公司：字节、阿里

**参考答案：**

Bad case 迭代和在线学习是 Agent 系统持续改进的关键闭环。

**1. Bad Case 收集流程：**

```
线上运行 → 用户反馈（点赞/踩/转人工）
    ↓
日志收集（完整对话轨迹 + 工具调用记录）
    ↓
自动标注（LLM 预标注 + 人工审核）
    ↓
分类归档（工具选择错误 / 参数错误 / 推理错误 / 安全问题 等）
    ↓
根因分析 → 修复策略
```

**2. 修复策略矩阵：**

| Bad Case 类型 | 根因 | 修复方式 |
|--------------|------|---------|
| 工具选择错误 | Prompt 不够清晰 | 优化工具描述 + 增加 Few-shot |
| 参数格式错误 | 模型输出不稳定 | 加强 Schema 约束 + 后处理 |
| 推理逻辑错误 | LLM 推理能力不足 | CoT 引导 / 换更强模型 / 微调 |
| 知识过期 | RAG 数据未更新 | 更新知识库 |
| 安全问题 | 越狱攻击 | 加强输入过滤 + Guardrails |

**3. 迭代节奏：**
- **实时修复**：安全类 bad case 立即修复（热更新 prompt）。
- **周迭代**：每周分析 bad case Top N，修复最影响指标的问题。
- **月迭代**：月度模型微调，用积累的偏好数据做 DPO。

**4. 是否做在线学习：**

| 方式 | 说明 | 适用条件 |
|------|------|---------|
| **不做在线学习** | 离线积累数据 + 定期微调 | 大多数生产系统的选择 |
| **Prompt 在线更新** | DSPy 等框架自动优化 prompt | 低风险，可快速尝试 |
| **LoRA 热更新** | 训练新 LoRA 权重并热加载 | 有足够 GPU 资源 |
| **真正在线 RL** | 实时用用户反馈更新模型 | 研究阶段为主，工业界很少用 |

**5. 不做在线学习的原因：**
- 稳定性风险：在线更新可能导致模型行为不可预测。
- 数据质量：线上反馈噪声大（用户误点、恶意反馈）。
- 合规要求：模型变更需要经过完整测试流程。
- ROI 低：定期微调的效果通常足够好。

> 面试加分点：说明你的 bad case 数量、修复周期、以及每次迭代带来的指标提升。

**Q43: Function Calling 和 Toolformer 的本质区别是什么？各自在训练/推理阶段如何工作？**
- 难度：⭐⭐⭐
- 岗位：算法岗重点
- 标签：#Function Calling #Toolformer
- 公司：字节(真题)

**参考答案：**

Function Calling 和 Toolsumer 代表了两种不同的"赋予 LLM 工具使用能力"的方法论。

**1. Function Calling：**

| 维度 | 说明 |
|------|------|
| **提出者** | OpenAI（2023年在 GPT 模型中首次引入） |
| **本质** | API 层面的能力——通过微调让模型输出结构化的工具调用 JSON |
| **训练阶段** | 用 `<对话, 工具定义, 正确调用>` 三元组数据做 SFT，部分模型还做了 RLHF |
| **推理阶段** | 模型输出特殊 token（如 `<tool_call{...}tool_call/>`），API 层解析后返回给开发者执行 |
| **特点** | 工具由开发者定义，模型只负责"决定调哪个、填什么参数" |

**2. Toolformer：**

| 维度 | 说明 |
|------|------|
| **提出者** | Meta AI（Schick et al., 2023） |
| **本质** | 模型层面的能力——模型自己学会在文本中**插入工具调用标记** |
| **训练阶段** | 自监督方式——模型自己在大量文本中找到适合插入 API 调用的位置，生成调用并执行，保留能降低 perplexity 的样本作为训练数据 |
| **推理阶段** | 模型在生成文本时自动决定是否插入工具调用（如 `[WikiSearch(query)]`），执行后将结果拼回文本继续生成 |
| **特点** | 模型自己发现"何时需要工具"，不需要外部工具定义 |

**3. 核心区别：**

| 维度 | Function Calling | Toolformer |
|------|-----------------|------------|
| **工具由谁定义** | 开发者定义（外部注入） | 模型自己学习（内部发现） |
| **训练数据** | 人工标注/蒸馏的工具调用数据 | 自监督生成（模型自己创造训练数据） |

**参考答案：**

旅行 Agent 是一个经典的 Multi-Agent 系统设计题，考察任务分解和协作设计能力。

**1. 任务拆解：**

```
用户需求："帮我规划一个五一去日本的5天旅行"
    ↓
┌─────────────────────────────────────────────┐
│                 任务分解                      │
├─────────────────────────────────────────────┤
```

**2. 子 Agent 职责划分：**

| 子 Agent | 职责 | 可用工具 | 输入 | 输出 |
|---------|------|---------|------|------|
| **协调 Agent（Planner）** | 整体规划、任务分配、结果汇总 | 无 | 用户需求 | 子任务列表 + 最终方案 |
| **偏好分析 Agent** | 提取用户偏好和约束 | 无 | 对话历史 | 结构化偏好（预算/城市/兴趣） |
| **航班 Agent** | 查询和比较航班 | 航班 API | 出发地、目的地、日期 | 航班推荐列表 |
| **酒店 Agent** | 查询和比较酒店 | 酒店 API | 城市、日期、预算 | 酒店推荐列表 |

| **行程 Agent** | 规划每日详细行程 | 地图 API、景点 API | 城市、天数、偏好 | 每日行程安排 |
| **预算 Agent** | 计算总费用并优化 | 计算器 | 各项费用 | 预算报告 + 优化建议 |

**3. 协作流程：**

```
    ↓

    ↓
```

**4. 关键设计决策：**
- **并行 vs 串行**：航班/酒店/天气可以并行查询，行程规划需要等前几步完成。
- **上下文传递**：每个子 Agent 的结果需要结构化（JSON），方便后续 Agent 消费。
- **用户交互**：在关键节点（如航班选择）可以让用户确认再继续。
- **容错**：某个 Agent 查询失败（如天气 API 不可用）不影响整体方案生成。

**Q45: 你的Agent如何处理工具调用失败(如API超时、返回空)？有设计重试、降级或用户澄清机制吗？**
- 难度：⭐⭐⭐
- 岗位：开发岗重点
- 标签：#容错机制 #降级策略
- 公司：字节(真题)

**参考答案：**

工具调用失败处理是 Agent 生产环境中的关键能力，需要**多层级防御**。

**1. 失败场景分类：**

| 失败类型 | 示例 | 严重程度 |
|---------|------|---------|
| **网络超时** | API 响应超过 10 秒 | 中 |
| **服务端错误** | HTTP 500/503 | 中 |
| **参数错误** | 400 Bad Request（LLM 填错了参数） | 低 |
| **认证失败** | API Key 过期 | 高 |
| **限流** | 429 Too Many Requests | 中 |
| **返回数据异常** | 空结果、格式不正确 | 低 |
| **业务逻辑错误** | "订单不存在" | 低 |

**2. 重试机制：**

```python
from tenacity import retry, stop_after_attempt, wait_exponential, retry_if_exception_type

@retry(
    stop=stop_after_attempt(3),                         # 最多重试3次
    wait=wait_exponential(multiplier=1, min=1, max=10), # 指数退避：1s, 2s, 4s
    retry=retry_if_exception_type((TimeoutError, ServiceUnavailableError))  # 只重试可重试的错误
)
async def call_api(tool_name, params):
    return await execute(tool_name, params)
```

- **指数退避**：1s → 2s → 4s，避免雪崩。
- **只重试可恢复错误**：网络超时/服务端错误可重试，参数错误不应重试。

**3. 降级策略：**

```
主工具失败
    ↓
备用工具（功能相似的其他 API）
    ↓
缓存结果（历史相似查询的结果）
    ↓
告知用户 + 建议替代方案
    ↓
转人工处理
```

**4. 用户澄清机制：**

当失败原因是用户输入模糊时，不应盲目重试，而是主动询问：

```python
def handle_failure(error, context):
    if isinstance(error, ParamError):
        # 参数错误 → 让 LLM 重新理解用户意图并补充参数
        clarification = llm.run(
            f"工具调用失败，缺少参数：{error.missing_params}\n"
            f"请基于以下对话上下文，向用户询问缺失信息：{context}"
        )
        return clarification  # "请问您的出发日期是哪天？"

    elif isinstance(error, NotFoundError):
        # 数据不存在 → 告知用户并提供替代方案
        return f"抱歉，未找到相关结果。您是否想查 xxx？"

    elif isinstance(error, TimeoutError):
        # 超时 → 建议稍后重试
        return "服务暂时繁忙，请稍后重试"
```

**5. 完整的容错流水线：**

```
LLM 生成工具调用 → 参数校验 → 执行（带超时）→ 结果校验 → 返回
       ↓              ↓            ↓              ↓
    格式修正？     参数补全     重试/降级       格式适配
```

**Q46: 在真实场景中，如何防止Agent泄露用户隐私或越权操作？从算法和系统层面谈谈你的设计。**
- 难度：⭐⭐⭐⭐
- 岗位：通用
- 标签：#安全性 #隐私保护
- 公司：字节、阿里(重要)

**参考答案：**

防止 Agent 泄露隐私或越权操作需要**算法层**和**系统层**的双重防护。

**1. 算法层面：**

**输入安全：**
- **Prompt Injection 检测**：用分类模型检测用户输入中是否包含注入攻击（如"忽略之前的指令"）。
- **敏感信息识别**：在用户输入到达 LLM 前，用 NER 检测并脱敏（如手机号、身份证号替换为 `***`）。
- **意图校验**：单独用一个 LLM 校验用户意图是否合理，过滤恶意请求。

**输出安全：**
- **输出过滤**：LLM 输出后，扫描是否包含敏感信息（其他用户的数据、系统内部信息）。
- **工具调用审查**：在执行工具调用前，检查是否越权（如普通用户试图查别人的订单）。
- **安全性评分**：对每条输出做安全性评分，低于阈值则拦截。

**2. 系统层面：**

| 层级 | 防护措施 |
|------|---------|
| **API 网关** | 限流、IP 黑名单、请求签名验证 |
| **认证鉴权** | 每个请求携带 token，验证用户身份和权限 |
| **数据隔离** | 不同用户的数据严格隔离（行级安全/分区） |
| **工具权限** | 每个工具设置权限等级，Agent 只能调用其权限范围内的工具 |
| **敏感操作确认** | 删除、支付等操作需要二次确认（Human-in-the-Loop） |
| **审计日志** | 记录所有操作，支持事后追溯 |
| **沙箱执行** | Agent 的代码执行操作在沙箱中进行 |

**3. 关键防护设计：**

```python
class SecurityMiddleware:
    async def pre_check(self, request):
        # 1. 身份验证
        user = verify_token(request.token)

        # 2. Prompt Injection 检测
        if is_injection(request.message):
            raise SecurityError("检测到潜在注入攻击")

        # 3. 敏感信息脱敏
        request.message = mask_sensitive_info(request.message)

        return request, user

    async def post_check(self, response, user):
        # 1. 输出过滤
        response = mask_sensitive_info(response)

        # 2. 工具调用权限检查
        if response.tool_call:
            if not has_permission(user, response.tool_call.tool):
                raise PermissionError("无权限执行此操作")

        return response
```

**4. 隐私保护：**
- **最小化原则**：只收集和访问任务所需的最少数据。
- **数据脱敏**：日志中不记录敏感字段（密码、身份证等）。
- **遗忘权**：用户可以要求删除其所有数据。
- **加密存储**：敏感数据加密后存储。

**参考答案：**

决策追溯和可解释性是 Agent 系统在信任关键场景（如金融、医疗）中的必要能力。

**1. 决策链记录机制：**

```python
class DecisionTrace:
    def __init__(self):
        self.chain = []  # 记录每一步决策

    def add_step(self, step_type, input_data, output_data, reasoning):
        self.chain.append({
            "step": len(self.chain) + 1,
            "type": step_type,          # "planning" / "tool_call" / "reasoning"
            "input": input_data,
            "output": output_data,
            "reasoning": reasoning,     # Agent 的思考过程
            "timestamp": now()
        })
```

**2. 回溯决策链的实现：**

当用户追问"为什么选这家酒店"时：

```
回溯决策链：
Step 1: 意图理解 → 用户需要北京5月1-3日住宿
Step 2: 工具调用 → 查询酒店（参数：北京、5.1-5.3、预算500/晚）
Step 3: 结果排序 → 按评分>位置>价格排序
Step 4: 选择理由 → 酒店 A：评分4.8、距天安门2km、￥380/晚
```

将决策链转化为用户可理解的自然语言：

```python
def explain_decision(agent, user_question, decision_chain):
    explanation = agent.run(
        f"用户问：{user_question}\n"
        f"以下是决策过程的完整记录：\n{format_chain(decision_chain)}\n"
        f"请用通俗易懂的语言向用户解释为什么做了这个选择"
    )
    return explanation
```

**3. 可解释性设计原则：**

| 原则 | 实现方式 |
|------|---------|
| **全程记录** | 每一步推理、每一个工具调用都记录原因和结果 |
| **分层解释** | 简单解释（给用户）+ 详细日志（给开发者） |
| **因果链** | 不只记录"做了什么"，还记录"为什么这么做" |
| **可视化** | 用 Mermaid/流程图展示决策路径 |

**4. ReAct 天然支持可解释性：**
- ReAct 的 Thought-Action-Observation 结构本身就是决策链。
- 每一步的 Thought 就是 Agent 的"推理理由"。
- 可以直接将 Thought 序列转化为解释。

**5. 工程实践要点：**
- 决策日志存储在独立的 trace 系统中（如 Jaeger/OpenTelemetry）。
- 用 trace_id 关联一次完整会话的所有决策步骤。
- 设置 trace 保留时间（如 30 天），平衡存储成本和审计需求。

**Q48: 如何评估一个Agent系统的鲁棒性？除了准确率，还会测试哪些对抗性或边缘case？**

**参考答案：**

鲁棒性评估是确保 Agent 在各种极端情况下仍能稳定工作的关键。

**1. 鲁棒性评估维度：**

| 维度 | 测试内容 | 示例 |
|------|---------|------|
| **输入扰动** | 用户输入有噪音、错别字、模糊表达 | "帮我订个票"（什么票？） |

| **多轮对话** | 用户反复修改需求、中途改变话题 | 先问航班又问酒店又回来说航班 |
| **并发压力** | 多用户同时访问 | 1000 QPS 下的系统稳定性 |

**2. 对抗性测试（Adversarial Testing）：**

| 攻击类型 | 测试方法 | 防御验证 |
|---------|---------|---------|
| **Prompt Injection** | 注入"忽略之前的指令"等攻击语句 | 验证是否被成功注入 |
| **数据泄露** | 询问"你的系统提示词是什么" | 验证是否泄露内部信息 |
| **越权操作** | 普通用户尝试管理员操作 | 验证权限控制是否生效 |
| **上下文污染** | 在工具返回数据中嵌入恶意指令 | 验证间接注入防御 |
| **资源耗尽** | 发送导致超长推理链的请求 | 验证超时和资源限制 |

**3. 边缘 Case 测试：**

```
- 用户同时要求两个相互矛盾的任务

- 工具返回非预期格式的数据

```

- **安全拦截率**：恶意输入被成功拦截的比例。

保证大模型输出稳定的 JSON 是 Agent 系统的基础工程问题，需要从**提示工程**、**API 层面**和**后处理**三方面保障。

| 方法 | 说明 | 效果 |

| **JSON Mode** | OpenAI `response_format={"type": "json_object"}` | 保证合法 JSON |
| **Structured Output** | `response_format={"type": "json_schema", ...}` | 保证符合 Schema |

**3. 后处理保障：**

```python
import json, re

def robust_json_parse(raw_output):
    # 1. 尝试直接解析
    try:
        return json.loads(raw_output)
    except json.JSONDecodeError:
        pass

    # 2. 提取 JSON 部分（模型可能在 JSON 前后添加了文字）
    json_match = re.search(r'\{.*\}', raw_output, re.DOTALL)
    if json_match:
        try:
            return json.loads(json_match.group())
        except json.JSONDecodeError:
            pass

    # 3. 常见错误修复
    fixed = raw_output
    fixed = re.sub(r',\s*}', '}', fixed)        # 去掉末尾多余逗号
    fixed = re.sub(r',\s*]', ']', fixed)        # 去掉数组末尾多余逗号
    fixed = fixed.replace("'", '"')             # 单引号改双引号
    fixed = re.sub(r'(\w+):', r'"\1":', fixed)  # key 加引号

    try:
        return json.loads(fixed)
    except json.JSONDecodeError:
        raise ParseError(f"无法解析 JSON: {raw_output[:200]}")

    # 4. Schema 校验
    validate_schema(parsed, schema)

    return parsed
```

**Q51: 问Agent的工具tool的设计，是否是workflow形式？**
- 难度：⭐⭐
- 岗位：开发岗重点
- 标签：#工具设计 #Workflow
- 公司：字节(真题)

**参考答案：**

Agent 的工具 Tool 设计可以采用**Workflow 形式**，也可以是**自由组合式**，取决于业务场景。

**1. 两种模式对比：**

| 模式 | 特点 | 适用场景 | 代表框架 |
|------|------|---------|---------|
| **Workflow（工作流）** | 预定义执行顺序，分支条件明确 | 流程固定、可预测性要求高 | n8n, Dify, LangGraph |
| **自由组合式（Agent 自主决策）** | Agent 根据情况自主选择工具和顺序 | 灵活场景、用户需求多样 | ReAct Agent, AutoGPT |

**2. Workflow 形式的工具设计：**

```yaml
# 示例：客服 Workflow
workflow:
  name: 订单查询与售后
  steps:
    - id: intent_classify
      type: classify
      inputs: [user_message]
      outputs: [intent]
      next:
        query_order: get_order_detail
        refund: check_refund_eligibility
        default: general_qa

    - id: get_order_detail
      type: tool_call
      tool: query_order_api
      inputs: [order_id]
      next: format_response

    - id: check_refund_eligibility
      type: tool_call
      tool: refund_policy_api
      inputs: [order_id]
      next: format_response

    - id: format_response
      type: llm_generate
      next: end
```

**优点**：行为可预测、易调试、性能稳定。
**缺点**：灵活性差，新场景需要修改 Workflow。

**3. 自由组合式的设计：**

```python
# Agent 自主决定调用哪些工具、以什么顺序
tools = [
    {"name": "query_order", "description": "查询订单状态"},
    {"name": "query_logistics", "description": "查询物流信息"},
    {"name": "refund", "description": "发起退款"},
    {"name": "knowledge_base", "description": "查询知识库"},
]

# Agent 根据用户输入自主规划工具调用序列
agent = Agent(tools=tools, strategy="react")
response = agent.run("我的订单怎么还没到？能退吗？")

# Agent 可能的执行路径：
# 1. query_order(order_id="xxx") → 订单状态：运输中
# 2. query_logistics(order_id="xxx") → 物流：已到本市
# 3. 根据结果决定：建议等待或可以退款
```

**优点**：灵活、能处理未知场景。
**缺点**：不可预测、调试困难、可能走弯路。

**4. 推荐的混合方案：**

```
核心流程用 Workflow（保证稳定性）
    ↓
关键决策点交给 Agent（保留灵活性）
    ↓
异常处理用自由组合式（应对意外情况）
```

实际项目中的做法：
- 主流程用 LangGraph 定义 Workflow（如：意图识别 → 工具调用 → 结果校验 → 回复生成）。
- 工具调用阶段允许 Agent 自主选择工具和参数。
- 异常路径有兜底 Workflow（如转人工流程）。

**Q52: agent调用工具不正确怎么办，采用sft或者强化学习怎么来解决？**
- 难度：⭐⭐⭐
- 岗位：算法岗重点
- 标签：#错误修正 #微调策略
- 公司：字节(真题)

**参考答案：**

Agent 调用工具不正确时，可以通过**SFT（监督微调）**和**强化学习（RL）**两种方式来修正。

**1. 问题分析——工具调用不正确的常见原因：**

| 原因 | 示例 | 最佳修正方式 |
|------|------|------------|
| 工具描述不清楚 | 描述太短导致模型误选 | 优化工具描述（不需要训练） |
| 意图理解错误 | 用户说"查快递"但调了退货工具 | SFT 微调 |
| 参数填充错误 | 把日期填到了城市字段 | SFT + 约束解码 |
| 不该调用时调用了 | 闲聊也触发工具调用 | SFT（加入 negative sample） |
| 复杂推理中选错工具 | 多步推理中间步骤选错 | RL 优化策略 |

**2. SFT 方案：**

**数据准备：**
```python
# 收集错误 case，人工标注正确答案
training_data = [
    {
        "messages": [
            {"role": "system", "content": "你是客服助手，有以下工具：..."},
            {"role": "user", "content": "我的快递到了吗？"},
            {"role": "assistant", "content": None,
             "tool_calls": [{"function": {"name": "query_logistics",
                                          "arguments": '{"order_id": "xxx"}'}}]}
        ]
    },
    # Negative sample：不应该调用工具的 case
    {
        "messages": [
            {"role": "system", "content": "你是客服助手，有以下工具：..."},
            {"role": "user", "content": "你好"},
            {"role": "assistant", "content": "你好！请问有什么可以帮你的？"}
        ]
    }
]
```

**训练策略：**
- 用错误 case + 正确标注构建训练集。
- Negative sample 占比 20-30%，防止模型过度调用工具。
- LoRA 微调，rank=16，alpha=32。
- 训练 3-5 epoch，学习率 2e-5。

**3. 强化学习（RL）方案：**

| RL 方法 | 做法 | 适用场景 |
|---------|------|---------|
| **RLHF** | 训练 Reward Model 评价工具调用的好坏，用 PPO 优化策略 | 大规模数据可用 |
| **DPO** | 直接用偏好对（正确调用 > 错误调用）训练，无需 Reward Model | 更稳定，推荐首选 |
| **RLAIF** | 用 LLM（如 GPT-4）作为 Reward Model | 降低人工标注成本 |

**DPO 实践：**
```python
# 偏好数据格式
dpo_data = {
    "prompt": "用户：我的快递到了吗？\n工具列表：[query_order, query_logistics, refund]",
    "chosen": '{"name": "query_logistics", "arguments": {"order_id": "xxx"}}',  # 正确选择
    "rejected": '{"name": "refund", "arguments": {"order_id": "xxx"}}'          # 错误选择
}
```

**4. 实际推荐：**

```
第一步：优化 Prompt 和工具描述（成本最低、见效最快）
    ↓ 如果不够
第二步：收集错误 case 做 SFT（中等成本、效果显著）
    ↓ 如果还需要优化
第三步：用 DPO 进一步优化（成本较高、提升最后几个百分点）
```

- 大多数情况下，**Prompt 优化 + SFT** 已经足够。
- RL/DPO 主要用于追求极致效果的场景。
- 不要上来就用 RL——先用最简单的方法解决问题。

> 面试加分点：说明你在项目中用 SFT 优化后，工具调用准确率从多少提升到多少。
